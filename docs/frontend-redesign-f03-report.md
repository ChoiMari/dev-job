## 범위와 계약 판단

- `AGENTS.md`, F00 감사, P03~P05·A04~A09, `docs/api-spec.md`의 공고·분석·북마크·개인 공고·지원 계약, F01의 App/Layout/States/API 경계를 확인했다.
- A07 `POST /api/jobs/collections/alio`는 `JobController.collectAlio`가 내부 수집 엔드포인트로 주석 처리했고, 로그인 세션·CSRF를 요구하지만 관리자 전용 권한 검사는 없다. API 문서는 목록·상세가 이 POST를 호출하지 않는다고 명시한다. F00에서도 버튼·프론트 호출이 없었다. 따라서 F03 화면에 수집 버튼을 만들지 않았다. 요구사항의 “현행 버튼 범위” 표현은 실제 구현과 충돌하며 제품 노출 여부는 별도 결정이 필요하다.
- A04~A06의 기존 검색·출처·정렬·페이지, 공고 상세·원문·북마크 후 분석·기술 일치도를 유지했다. 목록의 페이지 곱과 출처 형식을 먼저 검증하고, 외부 원문과 앱 내 지원 기록을 화면에서 구분했다.
- A08의 직접 등록·수정·삭제·본문 분석을 유지하고 개인 상세를 추가했다. 목록에서 상세를 열 수 있고 별도 상세 컴포넌트는 F09 라우트 연결을 기다린다. 직접 등록 공고는 공용 `JobPosting` ID로 취급하지 않는다.
- A09의 8개 상태 필터·허용 전이·이력·메모·시간대 포함 일정 기능을 유지했다. 상태값은 코드 텍스트로 표시하며 지원 기록은 외부 사이트의 실제 지원과 자동 동기화되지 않음을 안내한다.
- 기존 CUR-04·05·06과 EXT-IMG-07을 적용했다. 실제 공고·회사 로고·수치를 묘사할 추가 장식은 필요하지 않아 생성하지 않았다.

## 공유 경계 전달

- F07 후보 타입: `frontend/src/api/saved-jobs.ts`의 `JobCandidate = { kind: 'COLLECTED' | 'MANUAL'; id: number }`. `recommendationCandidate`는 수집 북마크의 `jobId`와 개인 공고의 `id`를 각각 사용한다. 통합 목록의 수집 행 `id`는 북마크 행 ID이므로 추천 후보 ID로 사용하면 안 된다. 기존 `matchRate`는 이 후보 계약과 별개다.
- F09: `#/bookmarks/{manualId}`를 `ManualJobDetailPage`에 연결하고 제목·활성 메뉴를 관심 공고로 지정해야 한다. `#/applications/{id}`는 현재 App에 연결되어 있으나 메뉴·직접 진입 회귀 확인이 필요하다. App, Layout, 전역 CSS, `api/index.ts`, 공용 자산 목록은 변경하지 않았다.
