# DevJob 확장 기능 요구사항 명세

상태: 요구사항 초안, Backend 단계별 구현 범위 확정 · 작성 기준: 2026-10-08

## 1. 문서 목적과 범위

이 문서는 기존 MVP 이후 확장 기능을 **사용자가 할 수 있어야 하는 일과 완료 판정 기준**으로 정의한다. EXT-01~08의 선택형 항목까지 모두 Backend 구현 범위에 포함한다. 구현은 [Backend 단계별 계획](extension-backend-roadmap.md)의 B00~B15로 나누고, **Backend API 전체를 먼저 검증한 뒤 Frontend를 연결**한다. 미확정 제품 정책과 외부 조건은 각 단계 착수 전에 결정한다. 특정 기술·제공기관·유료 서비스를 이 문서만으로 채택하지 않는다.

현재 제공되는 가입·로그인, 프로필·기술·프로젝트 관리, 저장된 채용공고 검색, 관심공고·지원 관리, 공고 기술 분석, 역량 비교, 기술 수요·Skill Gap, 대시보드 기능은 기준선이다. 아래 확장은 기존 기능의 사용자 데이터를 유지하고 기본 흐름을 방해하지 않아야 한다.

요구사항 출처: [기존 요구사항](requirements.md), [사용자 흐름](user-flow.md), [UI 명세](ui-spec.md), [MVP 이후 범위](api-spec.md), [미구현 기능 조사](frontend-missing-backend-apis.md).

## 3. 기능별 요구사항

### EXT-01 계정 설정

**현재 상태:** 설정 화면은 이메일 확인, 기존 관리 화면 이동, 로그아웃을 제공한다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-01-01 | 사용자는 현재 비밀번호를 확인받은 뒤 비밀번호를 변경할 수 있어야 한다. | 올바른 현재 비밀번호와 유효한 새 비밀번호로 변경된다. 잘못된 현재 비밀번호나 유효하지 않은 새 비밀번호는 거절되고 기존 비밀번호는 유지된다. |
| EXT-01-02 | 사용자는 계정 삭제 전에 삭제로 영향을 받는 기록과 되돌릴 수 있는지 여부를 확인할 수 있어야 한다. | 영향을 받는 정보와 결과가 화면에 명확히 표시된다. |
| EXT-01-03 | 사용자는 본인의 계정 삭제를 명시적으로 요청할 수 있어야 한다. | 정해진 확인 절차 이후 계정에 다시 로그인할 수 없고, 다른 사용자의 기록에는 영향이 없다. |
| EXT-01-04 | 사용자는 실제로 제공하는 알림의 종류별 수신 여부를 확인·변경할 수 있어야 한다. | 저장한 선택이 다시 접속해도 유지되고, 실제 발송·표시 동작이 선택과 일치하며 사용하지 않는 수단을 제공 중인 것처럼 표시하지 않는다. |

**B01 확정:** 비밀번호 변경에는 현재 비밀번호 확인이 필요하다. 성공하면 현재 세션에서 로그아웃하며 다른 기존 세션도 보호 API를 더 이상 사용할 수 없다. 재로그인 후 새 CSRF 토큰을 발급받는다. 새 비밀번호가 현재 비밀번호와 같으면 거절한다. 과거 비밀번호 이력은 저장하거나 검사하지 않는다.

**요구사항 확정 필요:** 계정 삭제 시 지원 이력 등 기록의 삭제·보존 범위, 알림 종류와 전달 방식. 이메일·카카오 알림은 기존 MVP 제외 범위이므로 이 문서만으로 도입을 확정하지 않는다.

### EXT-02 기술 숙련도와 경험

**현재 상태:** 사용자는 표준 기술을 검색해 보유 목록에 추가하거나 삭제할 수 있다. 숙련도·경험은 기록하지 않는다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-02-01 | 사용자는 보유 기술별 숙련도와 경험을 입력·수정·확인할 수 있어야 한다. | 기술마다 입력값이 구분되고 다시 접속해도 유지된다. |
| EXT-02-02 | 값을 입력하지 않은 기술도 계속 보유 기술로 관리할 수 있어야 한다. | 미입력이 기술 미보유나 최저 숙련도로 임의 해석되지 않는다. |
| EXT-02-03 | 기술을 삭제할 때 해당 기술의 숙련도·경험이 어떻게 처리되는지 일관되어야 한다. | 삭제·재등록 뒤 값이 정해진 정책대로 표시된다. |

**B02 확정 정책:** 숙련도는 1~5 정수, 경험은 0~600개월 정수이며 둘 다 미입력은 `null`이다. 미입력을 최저 숙련도나 기술 미보유로 해석하지 않는다. 프로젝트 기술은 보유 기술에 자동 등록하거나 경험 개월 수에 자동 합산하지 않는다. 보유 기술을 삭제하면 그 관계의 숙련도·경험도 삭제되고 재등록 시 두 값은 `null`이다. 기존 공고 적합도·Skill Gap은 보유 기술과 프로젝트 기술의 집합만 사용하며 숙련도·경험을 점수에 반영하지 않는다.

### EXT-03 개인 할 일

**현재 상태:** B03 Backend의 개인 할 일 API와 Frontend의 목록·등록·상세·수정·완료·삭제 화면을 연결했다. 대시보드 `nextActions`는 지원 상태와 다음 일정에서 계산한 읽기 전용 목록이며, 개인 할 일은 `personalTodos`로 구분한다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-03-01 | 사용자는 취업 준비 할 일을 직접 등록·조회·수정·삭제할 수 있어야 한다. | 할 일 목록과 상세 내용이 사용자별로 유지된다. |
| EXT-03-02 | 사용자는 할 일을 완료하고 완료 여부를 확인할 수 있어야 한다. | 완료 후 재접속해도 상태가 유지되며 다른 할 일의 상태는 변하지 않는다. |
| EXT-03-03 | 대시보드에 표시한다면 직접 등록한 할 일과 지원 기록에서 도출한 다음 행동을 구별할 수 있어야 한다. | 두 종류의 항목이 같은 사용자 행동으로 오해되지 않는다. |

**B03 확정 정책:** 제목만 필수(설명 선택). 기한은 선택이며 날짜·시각과 IANA 시간대를 함께 저장한다. 완료 취소를 허용하고 같은 완료 상태 요청은 상태와 변경 시각을 유지한다. 삭제 시각을 보존하고 일반 조회에서 숨긴다. 대시보드에는 별도 `personalTodos` 필드로 미완료 할 일을 표시하며 지원 기록에서 계산하는 `nextActions`는 유지한다. EXP 지급과 삭제된 할 일의 향후 보상 처리 정책은 EXT-06에서 별도로 결정한다.

### EXT-04 채용시장 확장 분석

**현재 상태:** 분석 완료 공고를 대상으로 기술별 수요와 표본 수를 보여준다. 경력·지역 분포와 기간별 기술 추이는 없다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-04-01 | 사용자는 경력 조건별 공고 분포를 확인할 수 있어야 한다. | 각 구간의 건수·비율과 집계 대상 공고 수를 함께 볼 수 있다. |
| EXT-04-02 | 사용자는 지역별 공고 분포를 확인할 수 있어야 한다. | 지역을 알 수 없는 공고의 처리 방식이 표시되고 합계가 집계 기준과 일치한다. |
| EXT-04-03 | 사용자는 선택한 기간에 따른 기술 수요 변화를 확인할 수 있어야 한다. | 기간별 기술 수치와 해당 기간의 표본 수가 함께 제시된다. |
| EXT-04-04 | 사용자는 결과가 적거나 없는 경우 통계의 한계를 알 수 있어야 한다. | 빈 기간·작은 표본·누락 정보가 전체 채용시장의 일반적 경향처럼 표시되지 않는다. |

**요구사항 확정 필요:** 집계 대상 출처와 기간, 날짜 기준, 경력·지역 구간, 미상 값 처리, 기술 수요의 필수/우대 합산 방식, 표본 부족 기준. 현재 수집 공고에는 지역·경력·날짜가 비어 있을 수 있다.

### EXT-05 별도 취업 관리

**현재 상태:** 채용공고에는 회사명이 있고, 지원 기록에는 상태와 다음 일정이 있다. B04 관심 기업, B05 이력서·버전, B06 면접 일정 Backend가 별도 리소스로 추가됐다. 프로필에는 학력·자격증 등이 있으며 학습 기록은 후속 단계다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-05-01 기업 관리 | 사용자는 관심 기업의 정보와 자신의 메모·관리 상태를 기록·확인할 수 있어야 한다. | 같은 이름의 서로 다른 기업을 근거 없이 합치지 않고 사용자별 기록이 유지된다. |
| EXT-05-02 이력서 관리 (B05 확정) | 사용자는 텍스트 JSON 이력서와 불변 버전을 저장·확인하고, 제목을 수정하며 새 버전을 만들고 이력서를 삭제할 수 있어야 한다. | 버전 ID·생성 시각과 본문이 유지되고 본인만 조회한다. 원문은 애플리케이션 암호화 후 저장한다. 삭제 즉시 조회 대상에서 제외하고 30일 후 영구 삭제한다. |
| EXT-05-03 면접 일정 | 사용자는 면접 일정을 등록·변경·취소·재활성화하고 선택적으로 지원 기록과 연결할 수 있어야 한다. | 오프셋 시각과 IANA 시간대가 일치하고 취소 상태가 재조회 시 유지된다. 연결된 지원은 본인 소유여야 하며 기존 지원 상태·이력·`nextScheduleAt`은 자동 변경되지 않는다. |
| EXT-05-04 학습 관리 | 사용자는 부족 기술에 대한 학습 목표와 진행·완료를 기록할 수 있어야 한다. | 학습 기록과 읽기 전용 Skill Gap 분석 결과가 구분된다. |

**요구사항 확정 필요:** 관심 기업과 공고의 공용 회사를 연결할지 여부, 학습 완료 기준과 Skill Gap 결과 변경 시 처리. B05는 파일 업로드·복구 API 없이 텍스트 JSON만 다루며 운영 DB 백업의 보존·삭제 정책은 미정이다. B06 면접 일정은 지원 연결 선택, 동일 시작 시각 허용, 취소 후 재활성화 가능, 기존 지원 `nextScheduleAt`과 독립 관리로 확정했다.

### EXT-06 캐릭터와 성장

**현재 상태:** 캐릭터 화면은 정적 미리보기와 기존 기능 링크를 제공한다. 성장·EXP·꾸미기 상태는 없다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-06-01 | 사용자는 자신의 캐릭터 상태와 현재 장착한 꾸미기 항목을 확인할 수 있어야 한다. | 다시 접속해도 같은 상태가 표시된다. |
| EXT-06-02 | 사용자는 사용 가능한 꾸미기 항목 중 하나를 선택해 적용할 수 있어야 한다. | 사용 불가능한 항목은 적용되지 않고, 선택 결과가 다시 접속해도 유지된다. |
| EXT-06-03 | 사용자는 활동에 따른 EXP·레벨 변화를 확인할 수 있어야 한다. | 같은 활동을 반복 요청해 보상이 중복되지 않고, 표시 수치와 실제 활동 기록이 일치한다. |
| EXT-06-04 | 사용자는 아이템 보상·목표·퀘스트의 획득 조건과 진행 상태를 확인할 수 있어야 한다. | 조건을 충족하지 않은 보상은 지급되지 않는다. |

**요구사항 확정 필요:** 첫 구현의 꾸미기 범위, 사용할 캐릭터 자산, EXP 대상 활동·지급량·레벨 기준, 취소/삭제 시 보상 처리, 기존 활동의 소급 적용 여부. 기본 꾸미기와 성장·보상은 별도 단계로 다룰 수 있다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-07-01 | 새 공식 출처를 선택한 경우 사용자는 그 출처의 저장된 공고를 기존 탐색 화면에서 구분해 볼 수 있어야 한다. | 출처·원문 링크·가능한 기본 정보가 정확히 표시된다. |
| EXT-07-02 | 반복 수집해도 같은 출처의 같은 공고가 중복 생성되지 않아야 한다. | 동일 공고 재수집 후 목록에 중복이 생기지 않는다. |
| EXT-07-03 | 한 출처에서 오류가 나도 다른 출처의 기존 공고와 사용자 기록을 볼 수 있어야 한다. | 외부 서비스 오류 중에도 저장된 공고·관심공고·지원 기록을 조회한다. |

**요구사항 확정 필요:** 우선 연동할 출처, 제공기관의 이용 자격·조건·호출 한도, 사용자가 수집을 직접 실행할지 여부, 갱신 주기, 누락 필드 표시 방식. Work24 일반 채용정보·상세와 새 공식 ATS는 각각 별도 범위로 결정한다.

### EXT-08 AI 기능 확장

**현재 상태:** 사용자가 요청한 공고의 기술을 추출·검증·저장하고 재사용한다. 이력서·자기소개서 분석과 의미 기반 매칭은 없다.

| ID | 사용자 요구사항 | 완료 판정 기준 |
| --- | --- | --- |
| EXT-08-01 이력서·자기소개서 분석 | 사용자는 본인이 제공한 문서의 분석을 명시적으로 요청하고 결과를 확인할 수 있어야 한다. | 본인 문서의 결과만 볼 수 있고, 입력 변경 후 이전 결과를 최신 결과로 오인하지 않는다. |
| EXT-08-02 분석 신뢰성 | 사용자는 진행·완료·실패를 구별하고 실패 시 재시도할 수 있어야 한다. | 유효하지 않은 결과를 완료로 표시하지 않고 AI 장애 중에도 문서·CRM 기록을 관리할 수 있다. |
| EXT-08-03 의미 기반 비교·추천 | 사용자는 기존 기술 일치도와 새 추천의 의미를 구분할 수 있어야 한다. | 추천 근거와 한계를 표시하며 합격 확률로 표현하지 않는다. |

**요구사항 확정 필요:** 분석할 문서의 입력·보관 범위, 분석 결과의 목적과 표시 항목, 사용자 동의·삭제 방식, 재분석 기준, 추천 평가 기준, 외부 서비스 비용과 데이터 처리 조건. 이력서 관리는 EXT-05-02의 범위와 함께 정한다.

## 4. 단계별 착수 전 결정할 제품 정책

한 번의 후속 작업에서 위 기능 전체의 세부 정책을 동시에 확정할 필요는 없다. 각 Backend 단계에 착수할 때 다음 정책을 먼저 결정하고, 결정 결과를 이 문서의 해당 절에 반영한다.

1. 사용자가 실제로 수행할 최소 행동과 첫 릴리스에 포함할 범위.
2. 입력·수정·삭제 뒤 사용자가 기대하는 결과와 기존 기록의 처리.
3. 기존 대시보드·지원·기술·공고·Skill Gap과 새 정보의 관계.
4. 통계 또는 점수의 의미, 표본·결측·중복 처리와 사용자에게 보여줄 한계.
5. 외부 서비스, 문서 파일, 알림 또는 AI가 필요한 경우 이용 조건·개인정보·비용 범위.

각 기능의 세부 설계는 해당 단계의 정책이 확정된 다음 [ERD](erd.md)·[확장 API 명세](extension-api-spec.md)·[확장 UI 명세](extension-ui-spec.md)에 작성한다. 이 문서의 완료 판정 기준이 충족되는지 기능별로 확인한다. 선택형 표현인 알림, 성장·보상·퀘스트, 새 출처, AI 문서 분석·의미 기반 추천은 **범위에 포함**하되 세부 동작은 단계별 결정 대기로 둔다.
