# DevJob 프론트 전면 개편 실행 계획

상태: F02~F08 커밋 반영, F09 코드·문서 통합 완료, F10 일부 검증 완료(전체 게이트 미완료) · 기준: 2026-10-11, B00~B15 Backend 완료. F00 결과는 [계약·기준선 기록](frontend-redesign-f00-audit.md), 통합 대조는 [F09 대조](frontend-redesign-f09-report.md), 실제 최종 검증 범위와 미실행 이유는 [F10 결과](frontend-redesign-f10-report.md)에 있다.

## 1. 목표·범위·현재 상태

목표는 [프론트 요구사항](frontend-redesign-requirements.md)의 P00~P20을 [시각 개편안](frontend-redesign-proposal.md)에 맞춰 구현하고 A01~A22 전체 API 묶음을 실제 UI에 연결하는 것이다. 비로그인 첫 접속의 `#/`은 공개 홈, 로그인 후 `#/`은 기존 대시보드로 분기한다. Backend·DB·REST 계약을 바꾸지 않고, 현재 세션/CSRF 클라이언트와 해시 라우트를 확장한다. 관리자 배치는 허용 계정에만 독립 화면으로 제공한다. 새 라이브러리, 외부 서비스, 자동 수집, 이메일/푸시 알림, 파일 업로드는 범위에 없다.

- `frontend/src/App.tsx`에는 인증·대시보드·공고·북마크·지원·프로필·프로젝트·할 일·관심 기업·시장/역량 분석·캐릭터·설정 라우트가 있다. F01에서 미인증 첫 `#/`의 공개 홈 분기를 추가했다. `Layout.tsx` 메뉴는 현재 구현된 보호 화면 범위에 맞춰져 있다.
- 기존 API 모듈은 주로 MVP와 B01~B04, B09 일부를 연결한다. 이력서·자기소개서·문서 분석·추천·면접·학습·알림·성장/퀘스트·계정 삭제·관리자 배치의 프론트 연결은 아직 계획 대상이다. 각 단계 착수 전에 실제 사용 여부를 `frontend/src/api`, 화면, 테스트로 다시 확인한다.
- Backend Controller와 [API 명세](api-spec.md), [확장 API 명세](extension-api-spec.md)를 대조해 A01~A22를 만들었다. 과거 디자인/확장 UI 문서의 “미구현” 표현은 Backend 완료 이전의 스냅샷이며 현재 구현 근거로 쓰지 않는다.
- 시작 시 `git status --short`는 깨끗했다. 작업 중 사용자의 새 변경이 생기면 해당 파일의 소유권을 다시 조정한다.

참조 문서: [MVP 요구사항](requirements.md)은 기존 기능 의미, [확장 요구사항](extension-requirements.md)은 EXT-01~08 기능 경계, [사용자 흐름](user-flow.md)은 기존 전이, [UI 명세](ui-spec.md)와 [확장 UI 명세](extension-ui-spec.md)는 화면 행동/접근성, [디자인 개편안](frontend-redesign-proposal.md)은 색·배치·반응형, [자산 매핑](frontend-asset-map.md)은 이미지 사용, [이 계획 규칙](../.agent/PLANS.md)은 단계별 산출물/검증 기준으로 사용한다. Backend DTO는 화면별 구현 직전에 해당 기능만 읽는다.

## 2. 공통 작업 규칙

1. 각 패키지 시작 시 대상 Controller·DTO, API 명세, 기존 프론트 API/화면/테스트와 [페이지별 이미지 기준](frontend-redesign-requirements.md#31-페이지별-이미지-작업-기준)을 비교한다. API 응답의 `null`, 페이지, 오류, 소유권, 비동기 상태를 기록한 뒤 구현한다. 불일치가 있으면 확인된 코드 동작을 기준으로 관련 명세를 동기화한다.
2. 각 패키지는 API 타입·요청 함수 → 화면/라우트/메뉴 → 상태 처리 → 해당 흐름 검증 순서로 완료한다. 공통 API 클라이언트와 전역 CSS를 여러 패키지가 동시에 수정하지 않는다.
3. 페이지 단위로 입력 보존, 저장 중 중복 클릭, 401/403/404/409/503, 빈 목록, 재시도, 접근성을 확인한다. 서버 상태가 필요한 결과는 재조회 또는 저장 응답으로 확정한다.
4. 새 화면이 서버에 없는 기능을 제안하면 해당 화면의 구현을 멈추고 계약과 영향만 별도 기록한다. 이번 계획에서 새로운 Backend API를 만들어 채우지 않는다.
5. 패키지마다 변경 파일·문서·검증 결과를 기록하고 통합 후 라우트/메뉴·API 전수 매핑을 다시 점검한다. 커밋·푸시는 요청 시에만 한다.
6. 페이지 작업에서 기존 [개편 이미지 산출물](redesign-image-manifest.md)이 맞지 않거나 새 장면이 필요하면 [이미지 제작 가이드](image-generation-brief.md)와 `imagegen` 스킬을 읽고 내장 `image_gen`으로 제작한다. 채택 파일을 `frontend/src/assets/redesign/`에 저장해 화면에 연결하고, 자산 목록에 경로·용도·접근성 처리를 갱신한다. 이미지 실패 시에도 정보·행동을 유지한다.

## 3. 의존성 그래프와 실행 단계

`F00 → F01` 후 `F02~F06`을 병렬로 진행할 수 있다. F03·F06이 통합되면 F07을, F04가 통합되면 F08을 시작할 수 있으며 F02·F05 완료를 기다릴 필요는 없다. F02~F08 전체가 통합되면 `F09 → F10`으로 진행한다. F03의 공고/북마크 기반 데이터 선택은 F07 추천 UI의 후보 선택에 필요하고, F06 문서 버전 화면은 F07의 문서 선택에 필요하다. F04 면접 화면은 F08 알림 연결 검증에 필요하다. 단계별 복사형 작업 지시는 [프론트 단계별 프롬프트](frontend-redesign-stage-prompts.md)를 따른다.

## 4. 병렬 작업 묶음과 충돌 통제

같은 단계의 패키지를 병렬 담당할 수 있지만 **각 담당자는 자기 폴더의 API·페이지·테스트와 해당 패키지 전용 새 이미지 파일만 수정**한다. `App.tsx`, `Layout.tsx`, `styles.css`, `frontend/src/api/index.ts`, 공통 컴포넌트, 공용 문서는 F01/F09 통합 담당이 소유한다. 병렬 담당은 이 파일과 공용 [이미지 산출물 목록](redesign-image-manifest.md)의 갱신 내용을 자신의 작업 요약에 남기고 F09에서 한 번에 반영한다. 동일 CSS 선택자와 이미지 자산 파일도 공동 편집하지 않는다.

F01 공통 경계: `App.tsx`가 해시 경로와 `GET /api/auth/me` 결과를 판별하고 기존 페이지를 보호한다. `session.ts`는 401과 일시 오류, 공개/인증/보호 경로의 순수 분기만 정의한다. `Layout.tsx`는 **구현된** 보호 화면의 제목·활성 메뉴·계정/로그아웃을 표시하며 `States.tsx`는 페이지가 제공한 문구와 재시도·빈 상태 행동을 렌더링한다. 각 패키지는 자기 페이지와 전용 CSS/API 모듈에서 상태를 관리하고, 새 경로의 App 분기·제목·메뉴 추가 요청을 통합 담당에게 전달한다. `api/index.ts`의 공통 세션/CSRF 진입점은 그대로 재사용한다. F02는 `PublicHome.tsx`의 콘텐츠·CUR-15를 완성한다. F03은 A07 수동 수집의 실제 제공 범위를 다시 확인하고, F06은 캐릭터 `progress` 타입을 보강한다.

| 병렬 단위 | 독립 수정 범위 예시 | 함께 시작 가능한 시점 | 병합 전 확인 |
| --- | --- | --- | --- |

| F04 | `pages/ProfilePage.tsx`, `pages/projects/`, `pages/todos/`, `pages/companies/`, 새 `pages/interviews/`, 전용 API·테스트 | F01 완료 | 면접 링크와 알림 연결, 공통 기술 검색 |

| F08 | 새 `pages/notifications/`, `pages/admin/`, 전용 API·테스트 | F04 완료 | 관리자 권한 표시, 알림 출처 링크 |

F02와 F08은 모두 설정/알림 A19와 맞닿는다. F02는 수신 **설정**만, F08은 알림 **목록/읽음**만 담당하며 타입 계약은 F00에서 확정한다. F04와 F05의 기술 검색 API는 기존 모듈을 읽기 전용 재사용한다. F03과 F07은 후보 타입을 공유하되 F07이 F03의 화면 파일을 수정하지 않는다. F06과 F07의 문서 버전 타입도 같은 방식이다. 실제 동시 작업 인원은 별도 실행 요청에 따라 정한다.
