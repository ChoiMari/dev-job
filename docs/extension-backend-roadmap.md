# DevJob 확장 기능 Backend 단계별 구현 계획

상태: B00 확인·B01~B04 Backend/Frontend 구현, B05·B06·B07·B08·B09·B10·B11·B12·B13 Backend 통합, 나머지 단계 계획 · 2026-10-09

## 목적과 적용 순서

[확장 요구사항](extension-requirements.md)의 EXT-01~08을 **Backend API → 계약 검증 → Frontend 연결** 순서로 진행한다. 현재 동작하는 MVP API는 [기존 API 명세](api-spec.md)가 기준이다. 확장 API의 후보와 계약 확정 항목은 [확장 API 명세](extension-api-spec.md)에 둔다. 이 문서는 작업 순서와 각 작업의 완료 조건을 정하며, 미확정 제품 정책을 임의로 채택하지 않는다.

각 단계는 **정책 결정 → 요구사항 갱신 → ERD/데이터 영향 확정 → API 요청·응답·오류 계약 확정 → Backend 구현·테스트 → 명세와 실제 응답 대조**의 순서로 닫는다. 단계 안에서 Controller·DTO·Service·Repository·migration·테스트를 필요한 범위로 묶는다. 이전 단계가 끝나지 않았더라도 의존성이 없는 단계를 착수할 수 있지만, 사용자 데이터 관계가 걸린 단계는 아래 선행 조건을 지킨다.

Frontend는 원칙적으로 B01~B15 Backend 단계의 계약 검증이 끝난 뒤 착수한다. B01~B03은 사용자 요청에 따라 검증된 각 Backend 계약을 먼저 Frontend에 연결했다. 다른 단계는 [확장 UI 명세](extension-ui-spec.md), 확정된 API 응답, 로딩·빈 결과·오류 상태를 대조한 뒤 착수한다. Backend 완료 전 가짜 응답을 실제 기능으로 노출하지 않는다.

### B00 통합 확인 (2026-10-08)

- 선행 조건인 MVP Backend는 인증·프로필·기술·프로젝트·저장 공고·북마크·지원·분석·대시보드 API와 Flyway V1~V11이 현재 작업 트리에 함께 있다. B01~B15의 확장 API는 아직 구현 단계가 아니며, B00에서는 새 API·Entity·migration을 만들지 않는다.
- COM-01~06에 적용할 기존 인증·CSRF·오류·페이지 계약은 [MVP API 명세 1~2절](api-spec.md)과 [확장 API 명세 B00 공통 기준](extension-api-spec.md#b00-공통-계약-기준)에 정리했다. 사용자 소유 데이터와 공통 공고·기술의 구분은 [ERD 4절](erd.md)을 따른다.
- 기존 `SecurityConfig`·`AuthController`·`GlobalExceptionHandler`와 페이지 DTO·검증 코드를 명세에 대조했다. Backend 비DB 회귀 테스트 104건이 통과했다. 이 검증은 새 확장 API의 실제 HTTP 응답이나 DB 통합 동작을 검증한 결과는 아니다.
- 아래 결정표의 항목은 B02 정책을 제외하고 **관련 단계 착수 시 결정 대기**다. B02는 숙련도 1~5 정수, 경험 0~600개월 정수, 삭제 후 재등록 시 값 초기화로 확정했다. B00 자체에는 새 제품 정책 선택이 필요하지 않다. 각 단계는 필요한 선택을 사용자에게 제시하고 확정 전에는 해당 API를 구현하지 않는다.

### B01 통합 확인 (2026-10-08)

- 사용자가 변경 성공 후 현재 세션 로그아웃·다른 세션 모두 무효화·현재 비밀번호 재사용 거절을 확정했다. 요구사항 EXT-01-01, ERD, 확장 API 명세 B01, MVP API 명세 2절과 인증 경계를 동기화했다.
- `PATCH /api/auth/password`와 Flyway V12의 사용자 인증 버전을 구현했다. 격리 PostgreSQL 17에서 성공 `204`/빈 본문·쿠키 삭제, 잘못된 입력 `400`, 현재 비밀번호 오류 `401`, CSRF 오류 `403`, 기존 세션 `401`, 다른 사용자 세션 유지, 재로그인, 같은 사용자의 동시 변경을 검증했다.
- Backend 일반 테스트 104건 통과. 격리 DB `dbTest` 85건 중 12건 실행·73건은 다른 단계 전용 DB 가드로 건너뛰었고 실행 실패는 없다. Frontend 및 B02~B15는 이 검증 범위가 아니다.

### B01·B02 main 통합 (2026-10-08)

- B01과 B02의 독립 커밋을 main에 반영했다. 두 작업이 각각 Flyway V12를 사용했으므로 B01의 사용자 인증 버전은 V12로 유지하고 B02의 기술 숙련도·경험 migration을 V13으로 순번 조정했다. 각 단계의 API·데이터 계약은 유지한다.
- 통합본 Backend 빌드·일반 테스트와 별도 임시 PostgreSQL 17의 B01·B02 DB 테스트가 통과했다. Flyway V1~V13과 JPA `validate`를 함께 확인했다.
- B01·B02 Frontend 커밋을 반영한 뒤 Frontend 빌드와 전체 테스트 63건이 통과했다.

### B03 개인 할 일 (2026-10-08)

EXT-03 정책을 사용자 선택에 따라 확정했다. 제목 필수·설명 선택, 오프셋 날짜·시각과 IANA 시간대의 쌍, 완료 취소 및 중복 요청의 상태 유지, 삭제 시각 보존, 대시보드 별도 `personalTodos`를 적용했다. [확장 API B03](extension-api-spec.md#b03--개인-할-일--ext-03-확정)과 [ERD B03](erd.md#b03-개인-할-일)에 계약을 기록하고 Backend V14·API·테스트를 구현했다. B10 EXP/보상 정책은 해당 단계에서 결정한다.

main 통합에서는 B03의 독립 브랜치 V12를 기존 B01 V12·B02 V13 다음의 V14로 조정했다. 통합본 Backend 빌드·일반 테스트와 별도 임시 PostgreSQL 17의 Flyway V1~V14·JPA `validate`·B03/B01 DB 테스트가 통과했다. Frontend 빌드와 전체 테스트 66건도 통과했다.

### B05 이력서·버전 관리 (독립 작업 트리, 2026-10-08)

사용자가 텍스트 JSON 전용, 기존 버전 불변·수정 시 새 버전, 삭제 즉시 비노출·30일 후 DB 영구 삭제, 복구 API 없음, AES-256-GCM 애플리케이션 암호화를 확정했다. `codex/b05-resume-versions`는 로컬 최신 main `35ea724`에서 분리했다. 독립 브랜치에서는 Flyway V15와 목록·상세·버전 생성·조회·제목 변경·삭제 API를 구현했다. main에서는 B04 V15 다음의 V16으로 배치한다. B12는 불변 `versionId`·`createdAt`을 원본 참조로 사용한다. 백업 보존 정책은 미정으로 남긴다. 독립 브랜치 검증 결과는 main 통합 검증과 구분한다.

main 통합본의 Backend 빌드·일반 테스트와 별도 임시 PostgreSQL 17의 Flyway V1~V16·JPA `validate`·B05 DB 테스트가 통과했다.

### B06 면접 일정 관리 (2026-10-09)

B06 독립 브랜치의 면접 일정 migration V15를 B04 V15·B05 V16 다음의 V17로 배치했다. 지원 연결은 선택 사항이며 기존 지원 상태·이력·`nextScheduleAt`은 자동 변경하지 않는다. 통합본 Backend 빌드·일반 테스트와 별도 임시 PostgreSQL 17의 Flyway V1~V17·JPA `validate`·B06 DB 테스트가 통과했다.

### B08 채용시장 확장 분석 (2026-10-08)

사용자가 경력·지역 분포와 기간별 기술 추이의 모수·게시일·중복·미상·비율·표본 부족·필수/우대 합산 기준을 확정했다. 공용 수집 공고 전체를 분포에 사용하고 기술 추이는 게시일이 있는 완료 분석 공고만 사용한다. 새 공식 출처는 공용 `JobPosting`에 저장되면 자동 포함하며 개인 직접 저장 공고는 제외한다. B11 인계 계약은 [확장 API B08](extension-api-spec.md#b08--채용시장-확장-분석--ext-04-확정)에 명시했다. 새 migration 없이 읽기 전용 API를 구현했고, 격리 PostgreSQL 17에서 결측·출처별 동일 외부 ID·기간 경계·빈 구간·기술 분모와 기존 `/api/analytics/skills` 회귀를 확인했다. Frontend는 이 단계에서 변경하지 않았다.

main 통합본의 Backend 빌드·일반 테스트와 별도 임시 PostgreSQL 17의 Flyway V1~V17·JPA `validate`·B08 DB 테스트가 통과했다. B11 공유 계약의 출처 미지정/지정 집계, 게시일 결측, 완료 분석 모수는 [확장 API B08](extension-api-spec.md#b08--채용시장-확장-분석--ext-04-확정)과 일치한다.

### B10 경험치·레벨·퀘스트·보상 API (2026-10-09)

사용자가 Todo 최초 완료당 10 EXP, 누적 EXP 레벨, 일회성 누적 완료 퀘스트 6종, 명시적 보상 수령, 취소·삭제 후 실적 유지, 기존 완료 Todo 소급 제외를 확정했다. 최신 로컬 main `85a25aa`에서 분리된 작업 트리에서 B03·B09의 커밋 반영을 확인하고 V22 활동 원장·보상 수령·기존 완료 표시와 API를 구현했다. Backend `build`·일반 테스트와 격리 PostgreSQL 17의 Flyway V1~V22·JPA 검증, 동시 완료·동시 수령·잠금 해제·소급 제외·기존 대시보드 격리를 확인했다. Frontend는 변경하지 않았다. 이 결과는 독립 작업 트리의 검증이다. main 통합에서는 B07 V22 다음인 V23으로 배치한다.

### B11 ALIO 관리자 수동 배치 (2026-10-09)

새 제공기관 대신 기존 ALIO 채용 API를 보강했다. 관리자 명시적 실행으로 정보통신 NCS 전체 페이지를 제목 선별 없이 수집하고, 출처별 마지막 실행·페이지·건수를 DB에 남긴다. 기존 3페이지 수집 계약은 유지한다. 격리 PostgreSQL 17의 Flyway V1~V18·JPA 검증 위에서 2페이지 21건 저장, 일반 제목 포함, 재실행 중복 21건, 동시 실행 차단, 두 번째 페이지 제공기관 장애 후 기존 21건 보존을 확인했다. 별도 CRM 회귀에서는 외부 장애·상세 부분 실패 중 공고·북마크·지원 조회와 ALIO/Work24 출처 필터를 확인했다. 실제 제공기관 3페이지 41건 중 유효하지 않은 `srcUrl` 14건은 검증한 공식 상세 화면 링크로 보완했다. 기존 ALIO DB는 20건에서 57건으로 늘었고 최종 배치가 신규 14건·중복 27건·거절 0건으로 완료됐다. 자동 배치와 관리자 Frontend는 후속 작업이다.

### B12 문서 AI 분석 (독립 작업 트리, 2026-10-09)

사용자가 자기소개서의 암호화·불변 버전 저장, 분석 요청마다 외부 전송 동의, 정형 개인정보 마스킹, 기술·강점·개선 제안 결과, 실패·멈춤 재시도와 완료 결과 재사용, 분석·문서 삭제 시 결과 즉시 삭제를 확정했다. 로컬 main `85a25aa`에서 분리한 작업 트리에서 B12 Backend만 구현했다. Flyway V22와 JPA 검증, 일반 빌드·테스트 및 격리 PostgreSQL 17의 B12 API 테스트를 실행했다. Frontend와 실제 외부 AI 호출은 하지 않았다. 이 기록은 독립 작업 트리 검증이며 main 통합에서는 V24로 배치한다.

권장 모델은 **구현 작업을 수행하는 Codex 모델**이며 DevJob 서비스가 호출하는 AI 모델이 아니다. [OpenAI 공식 모델 선택 가이드](https://developers.openai.com/api/docs/guides/model-selection)는 GPT-6.1 Sol을 복잡한 기술 작업의 균형형, Astra를 까다로운 분석·고난도 작업에 권장한다. 보안·외부 연동·AI 결과 검증·삭제처럼 설계 경계가 많은 단계에 Astra 또는 `high`를, 범위가 명확한 CRUD에는 Sol `medium`을 배정한 것은 이 프로젝트의 작업 난도에 따른 권장안이다. 모델 사용 가능 여부와 비용은 계정·제품 설정에 따라 다를 수 있다. [GPT-6.1 Sol 모델 설명](https://developers.openai.com/api/docs/models/gpt-6.1-sol)에 `medium`·`high` 지원이 명시되어 있다.

### B07 학습 목표 (독립 작업 트리, 2026-10-09)

사용자가 기술 연결 선택, 0~100 직접 입력 진행률, 100일 때만 완료, 완료 취소 허용, 삭제 시각 보존, UserSkill 자동 변경 없음과 활성 목표의 동일 기술·정리된 제목 중복 `409`를 확정했다. B07 독립 작업 트리는 로컬 main `85a25aa`에서 분리했다. B02 UserSkill과 기존 읽기 전용 Skill Gap API는 유지하고, 목표는 별도 테이블·API에 저장한다. 독립 작업 트리에서는 V24를 사용했으며 main 통합에서는 V22로 배치한다. 일회용 PostgreSQL 17에서 Flyway V1~V21·V24, JPA `validate`, B07 DB/API 테스트를 확인했다. 이 결과는 독립 작업 트리 검증이며 main 통합 검증과 구분한다.

## 병렬 작업과 합류 지점

아래의 `∥`는 **논리적 선행 관계가 없어 동시에 진행할 수 있음**을 뜻한다. 한 번에 모든 독립 단계를 실행하라는 뜻은 아니다. 같은 저장소의 migration·공통 문서·검증 DB 충돌을 고려해 초기에는 **2~3개 단계만 동시 진행하고 순차 통합**하는 것을 권장한다. B00에서는 전체 세부 정책을 한 번에 결정하지 않고, 각 병렬 단계가 시작할 때 필요한 결정만 확정한다.

| 구간 | 동시에 진행 가능한 작업 | 다음 합류 조건 |
| --- | --- | --- |
| 공통 출발 | B00 단독 | 공통 계약·단계 범위 정리 |
| 독립 기반 | B01 ∥ B02 ∥ B03 ∥ B04 ∥ B05 ∥ B06 ∥ B08 ∥ B09 ∥ B11 | 각 단계의 정책/외부 조건이 확정돼야 해당 작업 착수 |
| 첫 파생 | B07(B02 후) ∥ B10(B03+B09+보상 대상 활동 후) ∥ B12(B05 후) ∥ B13(알림 발생 기능과 종류 확정 후) | 선행 API 계약과 migration이 통합돼야 파생 단계 구현 |
| 추천 | B14(B11+B12 후) | 새 출처·문서 분석·기존 비교 API의 의미를 함께 검증 |

B04 기업과 B11 출처를 동시에 진행할 때는 기업 식별/연결 정책을 먼저 공유한다. B08 통계와 B11 출처를 동시에 진행할 때는 새 출처를 집계 모수에 포함할지 계약을 먼저 맞춘다. B13 알림은 실제로 알림을 발생시키는 기능의 이벤트 계약이 확정된 뒤 연결한다. 서로 다른 작업이 같은 migration 번호, 공통 예외 처리, `docs/api-spec.md`·`docs/erd.md`의 같은 절을 동시에 수정하지 않도록 담당 범위를 정하고 **한 단계씩 통합·회귀 검증**한다. 병렬 작업의 완료 보고는 해당 단계 브랜치의 결과이며 전체 Backend 완료를 뜻하지 않는다.
