# 취업지원 CRM 요구사항

## 1. 프로젝트 개요

### 1.1 프로젝트명

DevJob

### 1.2 프로젝트 목적

신입 및 주니어 개발자의 취업 준비 과정을 하나의 서비스에서 관리하고 분석할 수 있는 취업지원 CRM을 구축한다.

서비스는 외부 채용공고를 수집하고, 채용공고의 비정형 텍스트를 AI를 활용하여 구조화한 뒤 사용자의 보유 기술, 프로젝트 경험, 지원 이력과 연결한다.

이를 통해 사용자가 다음과 같은 활동을 하나의 서비스에서 수행할 수 있도록 한다.

- 채용공고 탐색
- 채용공고 요구 기술 분석
- 관심 공고 관리
- 지원 현황 관리
- 사용자 기술 관리
- 프로젝트 경험 관리
- 채용시장 기술 수요 확인
- 개인 기술 Gap 분석
- 학습 우선순위 확인

---

# 2. 제품 방향

## 2.1 서비스 성격

본 서비스는 **현대적인 취업지원 SaaS와 귀여운 픽셀 아트 게임 감성을 결합한 CRM**을 지향한다.

핵심은 게임을 만드는 것이 아니라 실제 취업 준비에 사용할 수 있는 전문적인 CRM에 픽셀 아트와 가벼운 게이미피케이션을 적용하는 것이다.

### 디자인 방향

```text
Modern SaaS
+
Cute Pixel Art
+
Chibi
+
Retro RPG
+
Productivity
+
Career Dashboard
+
Light Gamification
```

---

## 2.2 디자인 우선순위

UI 설계 시 다음 우선순위를 유지한다.

1. 정보 가독성
2. 사용성
3. 업무용 CRM으로서의 신뢰성
4. 일관된 디자인 시스템
5. 픽셀 아트 스타일
6. 게임적 장식

픽셀 아트는 서비스의 아이덴티티를 위한 요소이며 정보 전달과 사용성을 방해해서는 안 된다.

---

## 2.3 지양하는 방향

다음과 같은 디자인은 사용하지 않는다.

- 전체 화면을 오래된 게임 UI처럼 구성
- 과도한 장식
- 과도한 픽셀 폰트
- 과도한 애니메이션
- 정보 가독성을 떨어뜨리는 캐릭터 배치
- 화려한 게임 HUD
- 과도한 그림자
- 과도한 그라데이션
- 모든 화면을 게임처럼 구성

# 4. 사용자 문제

취업 준비 과정에서는 다음 정보가 여러 서비스와 문서에 분산되어 있다.

```text

     ↓
관심 공고 저장
     ↓
요구 기술 확인
     ↓
내 기술 확인
     ↓
지원
     ↓
지원 결과 관리
     ↓
반복적으로 요구되는 기술 확인
     ↓

     ↓
학습 우선순위 결정
```

본 서비스는 이 과정을 하나의 데이터 흐름으로 연결한다.

# 5. 핵심 데이터 흐름

서비스의 핵심 흐름은 다음과 같다.

```text
외부 채용공고 수집
        ↓
원문 및 기본 정보 저장
        ↓
채용공고 데이터 정규화
        ↓
AI 분석
        ↓
요구 기술 구조화
        ↓
기술명 정규화
        ↓
JobSkill 저장
        ↓
사용자 기술 / 프로젝트와 비교
        ↓
개인 기술 Gap 분석
        ↓
채용시장 기술 수요 분석
        ↓
지원 및 학습 의사결정 지원
```

AI는 단순한 부가 기능이 아니라 **채용공고의 비정형 정보를 서비스에서 활용 가능한 구조화 데이터로 변환하는 핵심 처리 단계**로 사용한다.

### 예시

```text

PostgreSQL
```

시스템에서는 기술명을 단순 문자열로 관리하지 않고 `Skill` 기준으로 관리한다.

S05에서 표준 기술·별칭 검색과 내 기술 추가·조회·삭제를 구현했다. 기존 이름·별칭은 같은 표준 ID로 연결하고 명시적인 사용자 추가에서만 새로운 유효 기술명을 표준 Skill로 생성한다. 중복은 `409`, 없는 ID·내 관계 없는 삭제는 `404`이며 세션의 사용자만 조회·변경한다. 구체적인 입력·검색 계약은 `api-spec.md` 3절을 따른다.

# 9. 채용공고 수집

## 9.1 외부 채용 데이터

공식적으로 사용 가능한 외부 채용 API를 통해 채용공고를 수집한다.

### MVP 우선순위

1. Work24 공채속보 목록 API
2. 사용자 요청에 따라 Saramin API 보완 연동 검토: 별도 이용 승인·용도 확인 후 추가

사용이 허용되지 않은 사이트의 무단 크롤링은 사용하지 않는다.

JobKorea 무단 크롤링은 MVP에서 제외한다.

S09(2026-10-06): 사용자가 S09의 Work24 연동 범위를 공채속보 목록으로 확정했다. 해당 범위의 구현·검증은 완료했으며 Work24 일반 채용정보목록·상세와 공채속보 상세는 S09 범위에서 제외한다. 공식 목록 필드만 S07 모델에 매핑하며 본문·경력·지역·미확인 날짜는 null이다. 공개 수집 API·자동 호출은 추가하지 않는다. 모의/격리 DB 회귀와 등록된 키의 실제 목록 1회 smoke를 통과했다. 승인된 저장·재배포·AI 용도와 호출 빈도 한도는 추가 확인이 필요하다. 공식 근거·현재 범위는 [architecture S09](architecture.md#s09-공식-접근계약-조사-2026-10-06)를 따른다.

사람인 후속 검토(2026-10-06): 공식 API에서 지역·경력·고용형태·게시일·마감 관련 필드를 확인했으며 별도 출처 공고로 보완한다. 공고 본문은 제공 필드로 확인되지 않아 본문 AI 분석의 해결책으로 가정하지 않는다. 개인/학생 개발자 신청이 가능한 형태로 보이지만 별도 API 승인이 필요하다. 현재 API 승인 대기로 사용자 요청에 따라 구현·호출을 보류하며 [공식 조사](architecture.md#사람인-보완-연동-공식-조사-2026-10-06)를 따른다.

# 14. AI 기반 채용공고 분석

## 14.1 AI의 핵심 역할

AI는 채용공고의 비정형 텍스트에서 시스템이 활용할 수 있는 구조화된 정보를 추출한다.

예를 들어 다음과 같은 원문을:

```text
Java/Spring Boot 기반 백엔드 개발 경험
JPA 및 PostgreSQL 사용 경험
Docker 기반 배포 경험 우대
```

다음과 같은 구조화 데이터로 변환한다.

```json
{
  "skills": [
    {
      "name": "Java",
      "requirementType": "REQUIRED"
    },
    {
      "name": "Spring Boot",
      "requirementType": "REQUIRED"
    },
    {
      "name": "JPA",
      "requirementType": "REQUIRED"
    },
    {
      "name": "PostgreSQL",
      "requirementType": "REQUIRED"
    },
    {
      "name": "Docker",
      "requirementType": "PREFERRED"
    }
  ]
}
```

---

## 14.2 요구 기술 유형

기술 요구사항은 최소한 다음 두 가지로 구분한다.

```text
REQUIRED
PREFERRED
```

- `REQUIRED`: 필수 또는 핵심 요구사항
- `PREFERRED`: 우대 또는 있으면 좋은 기술

# 15. AI 분석 처리 및 검증

AI의 응답을 그대로 데이터베이스에 저장하지 않는다.

```text
채용공고 원문
    ↓
AI 분석
    ↓
구조화된 JSON
    ↓
응답 형식 검증
    ↓
Skill 정규화
    ↓
DB 저장
```

잘못된 형식이나 허용되지 않은 데이터가 반환되는 경우 저장하지 않고 오류 처리 또는 재시도를 수행한다.

# 16. 기술명 정규화

동일한 기술이 여러 이름으로 표현되는 문제를 해결한다.

예:

```text
Postgres
PostgreSQL
postgresql
```

시스템에서는 하나의 기술로 통합한다.

```text
PostgreSQL
```

이를 위해 다음 개념을 사용한다.

```text
Skill
SkillAlias
```

AI가 추출한 기술명을 그대로 사용하는 것이 아니라 정규화 후 저장한다.

S05 공통 정규화 경계는 NFKC, 공백 축약·제거, 소문자 비교를 사용하고 기술 구두점은 유지한다. S12에서는 AI 응답의 JSON 구조·요구유형·기술명을 먼저 검증한 뒤 기존 표준명·별칭으로 정규화한다. 미등록 기술은 사용자 결정에 따라 공통 Skill·표준명 별칭을 생성하고 JobSkill에 연결한다. 동일 기술이 필수·우대로 중복되면 필수로 통합한다. 무효한 응답은 기술·완료 결과로 저장하지 않는다.

# 18. AI 연동 구조

AI 기능은 별도의 명확한 AI 처리 계층을 갖도록 설계한다.

구체적인 AI 프레임워크나 서버 분리 방식은 `architecture.md`에서 결정한다.

```text

        ↓

        ↓
Structured Output
        ↓
Validation
        ↓
Skill Normalization
        ↓
PostgreSQL
```

AI Provider 변경 가능성을 고려하여 특정 LLM 서비스에 핵심 도메인 로직이 강하게 결합되지 않도록 한다.

# 28. 개인 기술 Gap 분석

사용자의 보유 기술과 목표 직무 및 채용시장 요구 기술을 비교하여 부족한 기술을 보여준다.

기본적으로 다음 정보를 활용한다.

```text
희망 직무
+
채용시장 요구 빈도
+
사용자 보유 기술
+
프로젝트 경험
```

예:

```text
Docker
보유 여부: 없음
분석 완료 공고 100건 중 64건 등장 (필수 48건 / 우대 16건)
부족 기술 순위: 1위

Redis
보유 여부: 없음
분석 완료 공고 100건 중 36건 등장 (필수 10건 / 우대 26건)
부족 기술 순위: 2위
```

MVP에서는 필수 1·우대 0.5의 공고 건수를 분석 완료 공고 수로 나눈 규칙 기반 점수로 부족 기술을 정렬한다. 화면에는 상위 5개의 순위·기술명·등장률·필수/우대 실제 건수를 표시하고 점수나 HIGH/MEDIUM/LOW 등급은 표시하지 않는다. 분석 완료 공고가 5건 미만이면 순위를 보류하고 5~19건이면 `표본 적음`을 알린다. 등장률 구간은 점수 산정에 사용하지 않는다.

# 49. 코딩 에이전트 작업 원칙

코딩 에이전트는 다음 원칙을 따른다.

### 1. 문서 우선

구현 전에 관련 요구사항과 설계 문서를 확인한다.

### 2. 임의의 범위 확장 금지

요구사항에 없는 기능을 임의로 추가하지 않는다.

### 3. 계획 우선

여러 파일 또는 여러 기능을 변경하는 경우 구현 전에 작업 계획을 제시한다.

### 4. 승인 후 구현

사용자의 승인 없이 대규모 코드를 수정하지 않는다.

### 5. 기존 기능 보호

기존 기능을 임의로 삭제하거나 변경하지 않는다.

### 6. 기술 스택 준수

요구사항과 architecture 문서에 정의되지 않은 기술이나 라이브러리를 임의로 추가하지 않는다.

### 7. 디자인 원칙 준수

픽셀 아트 요소를 추가하더라도 정보 가독성과 CRM 사용성을 우선한다.

### 8. 검증

구현 후 실행 및 테스트를 수행하고 결과를 확인한다.

### 9. 문서 동기화

구현 결과로 요구사항 또는 설계가 변경되면 관련 문서를 업데이트한다.

# 53. 최종 제품 목표

최종 결과물은 다음과 같은 제품 경험을 목표로 한다.

> **실제로 취업 준비에 사용할 수 있는 전문적인 CRM이면서, 픽셀 아트 캐릭터와 가벼운 게임 요소를 통해 딱딱한 취업관리 서비스의 사용 경험을 개선하는 서비스**

따라서 본 프로젝트는

```text
취업 관리 SaaS
        +
AI 기반 채용 데이터 분석
        +
픽셀 아트 캐릭터
        +
가벼운 게이미피케이션
```

을 하나의 일관된 제품 경험으로 제공한다.

게임성이 CRM의 본질을 대체하지 않으며, **취업 준비에 필요한 정보의 정확성·가독성·사용성을 최우선으로 한다.**
