# DevJob 구현·검증 근거

## B01 · 비밀번호 변경 뒤 모든 세션 무효화 (2026-10-08)

- 결정과 근거: 메모리 세션 구조를 유지하면서 `users.credential_version`을 도입했다. 비밀번호 변경 시 사용자 행을 잠그고 BCrypt 해시와 버전을 한 트랜잭션에서 갱신한다. 현재 세션은 즉시 종료하고, 다른 세션은 보호 API 요청 시 저장 버전과 비교해 거절한다. 기존 세션에 버전 값이 없는 경우 0으로 간주해 첫 변경 뒤에도 우회하지 못하게 했다.
- 검증 근거: 격리 PostgreSQL 17에서 Flyway V12와 JPA 검증을 통과했다. 새 B01 DB 테스트 3건에서 성공 응답·현재/다른 세션·기존 세션·다른 사용자·입력/CSRF 오류·실패 시 해시 보존·동시 변경 한 건만 성공을 확인했다. Backend 일반 테스트 104건과 DB 테스트 실행 12건이 통과했고 다른 단계 DB 이름에 묶인 73건은 건너뛰었다.
- Frontend 연동에서 확인한 문제와 해결: 공통 API 클라이언트가 모든 `401`을 즉시 세션 만료로 처리해, 현재 비밀번호를 틀렸을 때도 로그아웃될 수 있었다. 비밀번호 변경 요청의 `401`은 자동 로그아웃을 보류하고 세션 조회로 자격 증명 오류와 만료를 구분한다. 브라우저 검증 중 세션 조회에도 같은 전역 처리를 쓰면 만료 안내가 사라지는 경합을 확인해, 이 조회만 전역 이벤트 없이 수행하도록 고쳤다. Frontend 빌드·테스트 61건, 390px 브라우저에서 `400`/`401`/`403`·성공 후 로그인·만료 안내를 확인했다. 브라우저 검증은 계약 모의 API를 사용했다.

## S15 · 표본 수를 드러내는 부족 기술 우선순위 (2026-10-07)

- 결정과 근거: 사용자·프로젝트의 표준 Skill ID를 합쳐 보유 기술을 제외하고, 목표 직무와 일치하는 완료 분석 공고에서 필수·우대 건수를 각각 집계한다. 사용자가 확정한 `100 × (필수 건수 + 0.5 × 우대 건수) ÷ 분석 완료 공고 수`로 부족 기술을 정렬하되 화면에는 상위 5개의 순위·기술·등장률·실제 건수만 보여준다. 분석 표본 5건 미만은 순위를 보류하고 5~19건은 `표본 적음`으로 불확실성을 드러낸다. 결과 테이블과 추가 외부 호출은 만들지 않았다.
- 검증 근거: 격리 PostgreSQL 17의 `devjob_s15_test`에서 Flyway·JPA validate와 S15 DB 테스트 3건이 통과했다. 완료/진행 중 공고와 직무 필터, 프로젝트 기술 제외, 다른 사용자 분리, 필수·우대 점수와 상위 5개, 4건 보류·20건 일반 표시, 인증·직무명 입력 오류를 확인했다. Backend 일반 테스트, Frontend 빌드·전체 테스트 51건, 390px Edge Chromium의 표본 부족·순위·오류 재시도·가로 넘침·JavaScript 오류 확인도 통과했다. 브라우저 검증은 모의 API 응답을 사용했으며 실제 외부 AI 호출은 포함하지 않았다.
- main 통합 검증 (2026-10-07): S15 커밋을 충돌 없이 반영했다. Backend build·일반 테스트 95건, Frontend build·테스트 51건이 통과했다. 새 격리 PostgreSQL 17의 `devjob_s15_test`에서 Flyway V1~V8·JPA `validate`와 S15 DB 테스트 3건이 통과했다. 통합본의 브라우저 흐름과 실제 외부 AI 호출은 재실행하지 않았다.

## S13 · 사용자별 기술 일치도와 페이지 경계 (2026-10-06)

- 결정: `UserSkill`과 소유 프로젝트의 `ProjectSkill`을 공통 Skill ID 집합으로 합쳐 같은 기술의 중복 기여를 막았다. 분석 완료 공고만 기술 필터에 포함하고, 기술 일치도는 매 조회 시 계산해 별도 저장값의 불일치를 피했다. 목록의 최소 일치도와 정렬은 SQL에서 페이지를 자르기 전에 적용해 페이지 총건수와 순서가 사용자별 결과를 반영하도록 했다.
- 검증 근거: 격리 PostgreSQL 17에서 S13 비교·목록 테스트 3개와 기존 공고 조회 회귀 7개가 통과했다. 보유 Java와 프로젝트 Java/React의 중복을 제거한 2/3 → 67%, 다른 사용자의 SQL만 1/3 → 33%, 분석 미완료 409, 기술 없음·보유 기술 없음, 일치도 0과 1 경계를 확인했다. Backend 일반 테스트와 Frontend 빌드·47개 테스트도 통과했다. 실제 로컬 브라우저에서 기술 선택·최소 50%·정렬·상세의 일치/부족 표시를 확인했다. 재현 범위는 [S13 검증](s13-validation.md)에 기록했다.
- main 통합 검증 (2026-10-07): S14의 시장 분석 API·화면과 문서 기록을 보존해 S13을 반영했다. Backend build·일반 테스트 94건, Frontend build·테스트 49건이 통과했다. 새 격리 PostgreSQL `devjob_s13_test`에서 Flyway V1~V8·JPA `validate`와 DB 테스트 실행 19건, 별도 `devjob_s14_test`에서 집계 회귀 2건이 통과했다. 실제 외부 AI 호출과 브라우저 흐름은 이번 통합에서 재실행하지 않았다.

## S06·S10·S11 · 병렬 기능 통합과 Flyway 순서 (2026-10-06)

- 통합 결정: 서로 V5를 추가한 세 작업의 SQL 내용을 유지하고 main에서 프로젝트 V5 → 북마크 V6 → 지원·상태 이력 V7로 배치했다. 기존 개발 DB의 Flyway 이력은 비어 있었고, 세 작업의 tmpfs 검증 DB는 재기동 뒤 이력 테이블이 없었다. 기존 DB의 초기화·이력 수정·repair 없이 새 Compose 프로젝트의 격리 PostgreSQL에서 V1~V7 적용과 JPA `validate`를 확인했다.

## S06 · 프로젝트 기술의 독립성과 관계 교체 검증 (2026-10-06)

- 결정과 Trade-off: 프로젝트 기술은 기존 표준 Skill ID를 참조하되 UserSkill을 자동 생성하지 않는다. 수정은 유지할 관계를 남기고 제거·추가할 관계만 반영해 `(project_id, skill_id)` 유일 키를 같은 flush에서 다시 삽입하는 충돌을 피한다. 수정·삭제는 프로젝트 행 잠금을 사용하고, 삭제는 해당 ProjectSkill과 Project만 같은 트랜잭션에서 제거한다. 공통 Skill·SkillAlias·UserSkill은 보존한다. 페이지 조회와 기술 관계 조회를 나눠 컬렉션 fetch join으로 페이지 건수가 왜곡되는 것을 피했다.
- 구현·문제 해결 근거: 실제 PostgreSQL 테스트에서 사용자 관계의 `findByUserId`가 DTO용 getter를 엔티티 필드로 해석해 목록 `500`을 반환했다. 명시적 관계 경로 `findByUser_Id`로 고쳐 사용자별 빈 목록·페이지 조회 회귀를 통과했다. 브라우저 페이지 이동 검사에서 새 페이지 번호와 이전 20개 결과가 잠깐 함께 표시되는 문제를 확인하고 페이지가 다른 결과를 숨기며 재조회 시 이전 결과를 비우도록 수정했다. 20+1 페이지와 두 번째 페이지 오류·재시도 검사가 통과했다.
- 검증 근거: 격리 PostgreSQL 17.11 tmpfs 컨테이너의 새 `devjob_s06_test`에서 Flyway V1~V5와 JPA validate를 확인했다. S06 DB 테스트 7개는 CRUD·중복 기술 ID의 단일 관계·유지/제거/재추가·타인 상세/수정/삭제 403·없는 기술 수정의 기존 데이터 보존·페이지/ID 경계·DB 날짜/유일성/FK 제약을 확인했다. 기존 인증 등 9개와 합계 16개가 통과했고 DB 이름이 다른 26개는 제외했다. 별도 새 `devjob_s05_test`에서 V1~V5 적용 후 기존 기술 정규화·보유 관계·동시성 회귀 6개가 모두 통과했다. 기존 S05 V3 이력 DB와 개발 DB는 사용하지 않았다.
- 화면·실행 근거: Backend build·일반 테스트 84개, Frontend build·테스트 33개가 통과했다. 실제 로컬 Backend·쿠키 세션으로 프로젝트 등록→새로고침→기존 기술 유지 수정→관계 제거→삭제·삭제 취소, UserSkill 빈 목록 유지, 원문 HTML 미실행·안전 링크, 로딩·저장 실패 입력 유지·목록/페이지 재시도, 404·잘못된 주소·로그아웃 경로 보호를 확인했다. 1440px Desktop 캡처와 768/390/320px Tablet·Mobile의 목록·상세·폼 넘침 및 표시된 폼 조작 대상 44px 검사를 수행했다. JavaScript pageerror는 없었다. 배포 HTTPS·실물 기기·S13 역량 비교는 이번 검증 범위 밖이다.
## S10 · 사용자별 저장 상태와 동시 중복의 DB 경계 (2026-10-06)

- 결정: 북마크는 지원·AI와 독립된 사용자·공고 관계로 저장한다. `CurrentUser`에서만 사용자 ID를 얻고 삭제도 복합 소유 키로 실행한다. 공고 목록의 저장 상태는 해당 페이지 ID 집합을 한 번에 조회해 공고마다 북마크 쿼리가 늘어나는 것을 피한다. UNIQUE·FK와 저장순 인덱스는 S10 단독 검증 당시 V5에 추가했고, main 통합에서는 같은 SQL을 V6에 배치했다. 기존 테이블·데이터는 변경하지 않았다.
- 검증 근거: PostgreSQL의 `ON CONFLICT`로 동시 저장 두 요청을 201 하나·409 하나로 처리하고 관계 1행을 확인했다. 실제 DB/HTTP 검증에서 타인 목록·공고 상태 분리, 입력 userId/header 무시, 타인 삭제 404와 원래 관계·공고 보존, 정확한 페이지·FK/UNIQUE 거부를 확인했다. Backend 일반 83개·격리 DB 실행 23개(S10 7개 포함), Frontend 33개·양쪽 build가 통과했다. 다른 DB 전용 19개는 skip했다.
- 화면 상태 근거: 실제 쿠키 세션에서 저장→상세/새로고침→관심 목록→해제, 다른 탭의 선행 저장/해제에 따른 실제 409/404 후 재조회, 지연된 mutation 도중 공고 전환, 페이지 마지막 항목 해제, 오류·재시도와 사용자 분리를 확인했다. 이전 상세 응답은 적용 대상 ID가 같을 때만 반영한다. 1440·768·390·320px 배치와 hover computed 색상·캡처를 확인했다. 재현 및 미실행 범위는 [S10 검증](s10-validation.md)에 기록했다.

## S11 · 동시 상태 변경과 이력의 원자성 (2026-10-06)

- 결정과 Trade-off: 지원 상태와 이력을 같은 트랜잭션으로 저장하고, 지원 행의 비관적 잠금으로 메모·일정 수정과 상태 전이를 직렬화한다. 추가 버전 필드/API 변경 없이 최신 상태에 전이 규칙을 적용한다. 동일 사용자·공고 등록은 UNIQUE로 보호하며 공고 목록의 실제 상태는 페이지 ID에 대해 일괄 조회한다.
- 실제 PostgreSQL 근거: 새 tmpfs 격리 DB의 동시 등록에서 201/409 각 한 번·지원 1행·초기 이력 1행, 동시 철회에서 200/409 각 한 번·이력 1행 추가를 확인했다. 생성·전이 뒤 강제 rollback에서 지원과 이력의 동반 rollback을 확인했다. 최초 이력·전이·소유권·부분 PATCH·실제 지원일 유지도 API 테스트로 검증했다.
- 검증: Backend build 일반 85개, 격리 DB 실행 25개(S11 9개·S08 7개 포함), Frontend build·테스트 34개가 통과했다. 다른 단계 전용 DB 19개는 이름 가드로 skip했다. 실제 세션 브라우저에서 등록→메모/일정→최종 상태→이력, 사용자 분리, 20+4 페이지, 실패 초안 유지·재시도, 320~1440px 화면을 확인했다. 메모 기본값이 textarea 라벨 이름에 섞인 접근성 문제는 명시적 label 연결로 고치고 재검증했다. 자세한 근거와 미실행 범위는 [S11 보고](s11-validation.md)에 있다.

## S04·S05·S08 · 병렬 변경 통합과 Flyway 적용 순서 (2026-10-06)

- 결정과 근거: S04 프로필과 S05 기술이 모두 V3 migration을 추가해, 통합본은 사용자 V1→공고 V2→프로필 V3→기술 V4 순서로 조정했다. 기존 개발 DB의 이력은 비어 있고 S05 작업 DB에는 기술 V3이 이미 적용되어 있어 그 DB에 통합본을 직접 실행하지 않았다. 기존 이력 수정·DB 초기화 없이 새 Compose 프로젝트의 네 격리 DB에서 V1~V4 적용과 JPA `validate`를 확인했다.

- IT 필터 검증: Backend 일반 테스트 104건, 격리 PostgreSQL DB 테스트 실행 20건(56건은 환경 조건으로 제외), Frontend 테스트 55건과 양쪽 빌드가 통과했다. 수정된 로컬 서비스에서 실 ALIO 정보통신 첫 페이지를 수집해 IT 제목 공고 2건을 저장하고 URL이 유효하지 않은 1건을 제외했다. 같은 페이지의 한글 `전산` 검색을 다시 수집해 기존 2건 갱신·오류 0건을 확인했고, 저장 공고의 기본 IT 필터와 회사 검색을 브라우저에서 확인했다.
- 최종 목록 UX 분리: 수집 POST와 Adapter→정규화→DB 저장 경로는 유지하고 사용자 목록의 수집 입력을 제거했다. `JobSource.code` 출처 필터를 일반 JPA 검색과 일치도 정렬 SQL 검색에 함께 적용해 정렬·페이지 전체 건수가 일치하도록 했다. - 개발 직무 데이터 품질 보정과 개인 관심공고 설계: 실제 ALIO 정보통신·진행 중 목록은 41건(20·20·1건)이었고 기존 첫 페이지/제목 기준에서는 `정보개발` 공고가 누락됐다. 요청당 3페이지 수집과 개발 신호 보강 후 격리 PostgreSQL에 IT 제목 공고 5건을 저장했으며 `GET /api/jobs?q=개발&itOnly=true&role=DEVELOPMENT`의 실제 결과를 확인했다. 브라우저에서는 짧은 `개발`을 본문까지 검색할 때 전산행정 공고가 섞여 2건이었고, 짧은 검색어의 본문 검색을 제외하자 개발 제목 1건만 표시됐다. 공공기관 출처만으로 개발 공고량이 충분하지 않다는 한계도 확인됐다. 직접 등록 공고는 공유 JobPosting과 분리하고 Application 두 FK의 정확히 하나 조건·개인 URL 유일성·소프트 삭제로 소유권과 지원 이력 보존을 검증했다.
- 관심공고 AI 분석 문제와 해결: 로컬 백엔드에서 키 미설정 및 이전 키의 제공기관 `401 authentication_failed`를 확인했다. 교체한 코디세이 키는 `/v1/models` 인증 `200`과 실제 구조화 분석 smoke를 통과했다. 개인 공고는 사용자가 붙여넣은 본문만 명시적으로 분석해 별도 결과로 저장하고, 공용 공고 기술 통계에 섞지 않는다. Flyway V11과 격리 PostgreSQL 통합 테스트에서 소유권·완료 기술·목록 표시·본문 수정 시 무효화를 확인했다. 실제 브라우저에서는 개인 공고의 필수 Java·Spring Boot, 우대 Docker·PostgreSQL과 수집 공고의 완료 분석 기술이 관심 목록에 표시됐다. 키와 제공기관 응답 원문은 기록하지 않았다.
## B02 · 보유 기술 숙련도·경험 (2026-10-08)

- 결정과 Trade-off: 기존 `Skill` 응답과 적합도·Skill Gap의 기술 집합 계산을 유지하기 위해 숙련도 1~5·경험 0~600개월의 nullable 값을 `UserSkill` 관계에만 저장했다. 삭제 후 재등록은 새 관계로 시작하며 이전 값을 복원하지 않는다.
- 문제와 해결: 첫 격리 DB 테스트에서 JPQL 벌크 UPDATE 뒤 PATCH 응답이 이전 null 값을 반환했다. 관리 중인 JPA 객체가 UPDATE를 반영하지 않은 원인을 확인하고 수정 전 flush·수정 후 영속성 컨텍스트 clear로 재조회했다.
- 검증 근거: 일회용 PostgreSQL 17 `devjob_b02_test`에서 Flyway V1~V12·JPA `validate`와 B02 DB 테스트 2건이 통과했다. 기존 공용 기술 검색 응답 형식, 부분 수정·명시적 null·사용자 격리·삭제/재등록을 확인했다. 같은 일회용 컨테이너의 별도 DB에서 기존 공고 적합도·Skill Gap DB 테스트도 통과해 계산 계약을 회귀 확인했다. Backend 일반 테스트 105건도 통과했다. 다른 단계 이름의 DB 가드 테스트는 이번 DB 실행에 포함하지 않았다.
- main 통합: B01과 B02가 각각 Flyway V12를 사용해 합류 시 버전이 중복됐다. B01을 V12로 유지하고 B02를 V13으로 조정했으며, 위 B02 단독 검증 기록의 V12는 통합 전 브랜치에서 실행한 버전이다. 통합본 Backend 빌드·일반 테스트와 별도 임시 PostgreSQL 17의 B01·B02 DB 테스트에서 Flyway V1~V13·JPA 검증이 통과했다. 각 Frontend 커밋을 반영한 뒤 Frontend 빌드·전체 테스트 63건도 통과했다.
