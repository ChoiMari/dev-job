# DevJob 구현·검증 근거

## S04 · 세션 소유권과 프로필 데이터 분리 (2026-10-06)

- 결정: 프로필 API는 세션 사용자 ID로만 조회·저장하고 `profiles.user_id` UNIQUE와 FK로 사용자당 최대 한 건을 보장한다. 이메일은 기존 `users.email`에만 남기고, 변경 시 같은 트랜잭션에서 중복을 검사한다. 다른 사용자 ID를 요청 파라미터·헤더로 보내도 선택에 사용하지 않는다.
- 검증 근거: 격리 PostgreSQL 17의 `devjob_s04_test`에서 Flyway V1→V2→V3 적용과 JPA 매핑 검증 후 `build dbTest`가 통과했다. S04 DB 테스트는 최초 `404`→`201`→재조회→수정 `200`, 타 사용자 분리, 이메일 중복·입력·CSRF 오류를 확인했다. 일반 테스트 49건, DB 테스트 11건(S07 전용 8건은 DB 이름 조건으로 건너뜀), Frontend 테스트 21건과 빌드가 통과했다. 로컬 브라우저에서 가입·로그인 후 프로필 빈 상태→최초 저장→새로고침 재조회→수정 성공을 확인했다. 브라우저 테스트 데이터가 남은 상태의 재실행에서 전체 행 수를 가정한 S04 테스트가 실패해, 사용자별 조회를 검증하도록 수정했다.

## S05 · 정규화 경계와 동시 기술 등록의 유일성 (2026-10-06)

- 결정과 Trade-off: API 명세의 사용자 기술 추가는 유효한 새 이름을 표준 Skill로 생성하도록 유지했다. 같은 정규화 규칙을 AI/외부 입력에도 재사용하되 `resolveExisting`은 기존 목록만 조회하고 미해결 이름을 반환한다. 명시적 사용자 추가용 `resolveForUser`와 분리해 후속 AI 출력이 검증 없이 공통 기술 목록을 늘리지 않도록 했다. S05는 외부 호출이나 AI 결과 저장을 구현하지 않았다.
- 구현 근거: NFKC·Unicode 공백 축약·ROOT 소문자 키를 사용하며 구두점을 보존한다. 표준명 자체도 별칭의 UNIQUE 키 공간에 예약한다. 표준 기술·별칭·사용자 기술 관계에 DB 유일 제약을 두고 PostgreSQL `ON CONFLICT`를 사용해 동시 요청의 사전 조회 경쟁과 트랜잭션 오류를 피한다.
- 검증 근거: `SkillConcurrencyDatabaseTest`는 같은 사용자의 대소문자가 다른 두 이름을 동시에 등록해 성공 201 하나·중복 409 하나, Skill 1행·표준명 별칭 1행·UserSkill 1행을 확인했다. `SkillDatabaseTest`는 Postgres/PostgreSQL 중복, 미등록 외부 입력의 무저장, 사용자 새 이름 생성과 다른 사용자의 표준 ID 재사용, 타인 삭제 요청의 404 및 원래 관계 보존, 없는 FK의 DB 거부를 검증했다. C++/C#, JPA/Spring Data JPA를 임의로 병합하지 않는 것도 확인했다.
- 실행 근거: 기존 개발 DB와 분리한 PostgreSQL 17.11 컨테이너의 `devjob_s05_test`에서 V1·V2·V3 Flyway 적용과 JPA validate를 확인했다. Backend build·일반 테스트 49개·실행된 DB 테스트 15개, Frontend build·테스트 23개가 통과했다. S07 DB 테스트 8개는 별도 DB 이름 가드로 skip했다. 실제 로컬 브라우저에서 별칭 추가→새로고침 조회→삭제→빈 목록 재조회, 중복 오류, 미등록 이름의 생성·관계 삭제, 로그아웃 후 보호 경로 차단을 확인했다. 1440·768·390·320px 너비의 확인 화면에 가로 넘침과 높이 44px 미만의 표시된 버튼·입력이 없었다. 배포 HTTPS와 실물 기기는 미검증이며 S04 전체 프로필 화면과의 통합 검증은 남아 있다.

## S02-V · 픽셀 아이덴티티와 상태 가독성의 공통 기준 (2026-10-06)

- 결정과 Trade-off: 본문·폼·카드는 시스템 웹 폰트와 일반 SaaS 배치를 유지하고, 픽셀 표현은 로컬 SVG 아이콘·정적 치비 캐릭터·배지·캐릭터 받침에 제한했다. 정수 좌표와 공유 CSS 팔레트로 작은 화면에서도 같은 캐릭터를 재사용하며 외부 이미지·폰트 요청과 제품 의존성을 추가하지 않았다. 성장·꾸미기 데이터는 만들지 않았다.
- 구현 근거: `PixelArt.tsx`의 아이콘·캐릭터·배지와 `States.tsx`의 성공 안내를 기본 화면·공통 상태·인증 화면에서 공유한다. 색상 외에 아이콘·문구·status/alert 의미를 함께 제공하며 가입 완료에는 같은 성공 컴포넌트의 compact 표시를 사용한다. 로딩의 밝기 변화는 모션 감소 설정에서 중단한다.
- 검증 근거: 프로덕션 빌드를 Edge Chromium 154에서 1440×1000, 768×1024, 390×844, 320×812로 실행했다. 모의 인증 응답으로 기본 화면·네 가지 공통 상태·오류 재시도·접이식 메뉴·로그인 오류/처리 중·가입 확인 불일치/중복/완료·새로고침을 확인했다. 검사한 화면에서 가로 넘침과 44px 미만의 버튼·입력·메뉴 링크, JavaScript pageerror가 없었고 키보드 본문 이동·포커스와 모션 감소도 통과했다. 화면 캡처로 캐릭터·배지·오류·폼 줄바꿈을 확인했다.
- 측정·회귀: 공유 토큰의 본문/흰 배경 대비 14.70:1, 설명/흰 배경 6.55:1, 주요 버튼 7.85:1, 성공/민트 6.36:1, 오류/핑크 6.21:1, 입력 경계/흰 배경 3.38:1을 색상값으로 계산했다. `pnpm build`와 기존 API·인증 테스트 19개가 통과했다. 인증/API 소스는 변경하지 않았으며 실제 Backend 연동·실물 모바일 기기·다른 브라우저 검증은 이번 UI 단계에서 재실행하지 않았다.

## S03 · 쿠키 세션의 서버 무효화와 CSRF 경계 (2026-10-05)

- 결정: 사용자가 서버 세션 + HttpOnly 쿠키를 선택했다. 로그인 응답 JSON을 유지하고 서버에서 즉시 로그아웃을 반영하는 대신, CSRF 보호·같은 출처 제공을 요구하고 서버 재시작 시 로그인 상태가 사라지는 trade-off를 수용했다. 별도 토큰 폐기 DB·세션 공유 서비스는 추가하지 않았다.
- 검증 근거: `AuthHttpTest`는 실제 Tomcat·PostgreSQL에서 로그인 전 쿠키 재사용 `401`, 로그인 전 CSRF 토큰 재사용 `403`, 로그아웃 후 인증 쿠키 재사용 `401`을 확인한다. HttpOnly·Secure·SameSite=Lax 속성도 검사한다. `AuthDatabaseTest`는 두 사용자 세션에서 입력 ID로 다른 계정을 선택할 수 없고 한 계정의 로그아웃이 다른 세션을 종료하지 않음을 확인한다.
- 입력 경계: BCrypt의 72바이트 한계를 고려해 문자 수 검사에 UTF-8 바이트 검사를 추가했다. `AuthSecurityTest`에서 25개 한글 문자(75바이트)의 가입 요청을 `400`으로 차단했고 `AuthServiceTest`에서 정확히 72바이트는 해시·대조 가능하고 73바이트는 검증에서 거부되는 것을 확인한다. 비밀번호·해시는 API와 세션 주체에 포함하지 않는다.
- 브라우저 근거: 별도 검증 DB에서 가입 완료, 잘못된 비밀번호 오류, 정상 로그인, 새로고침 후 유지, 로그아웃, 보호 경로 재접근 시 로그인 화면 이동을 직접 확인했다. 배포 HTTPS와 30분 실시간 만료 대기는 실행하지 않았다.

## 2026-10-05 · S07 채용공고 모의 수집의 실패 격리와 중복 처리

- 결정: 외부 호출 중에는 DB 트랜잭션을 유지하지 않고, 출처 등록과 각 공고 저장을 독립 트랜잭션으로 처리했다. 회사와 공고는 같은 저장 트랜잭션에 두어 공고 저장 실패 시 회사도 롤백한다.
- 검증 근거: `JobCollectionDatabaseTest`에서 PostgreSQL이 허용하지 않는 NUL을 본문에 주입해 실제 DB 저장 오류를 발생시켰다. 실패한 공고와 회사는 저장되지 않고 앞뒤의 정상 공고·회사 두 건이 저장됐다. 외부 Adapter 예외 후 기존 공고·회사 조회 및 후속 수집이 정상 동작하고 호출자 트랜잭션이 rollback-only가 되지 않는 것도 확인했다.
- 결정과 Trade-off: `(job_source_id, external_id)` 유일 키에 더해 출처 행 잠금으로 같은 출처의 동시 저장을 순서대로 처리한다. 같은 출처의 처리량보다 중복 공고·고아 회사 방지를 우선했다. 회사명은 기업 고유 식별자가 아니므로 신규 공고끼리 같은 이름만으로 회사를 병합하지 않는다.
- 검증 근거: 동시에 같은 공고를 수집한 두 실행에서 생성 1건·중복 1건, 공고·회사·출처 각각 1건을 확인했다. 반복 수집은 기존 원문·회사 연결·시각을 보존하고, 다른 출처의 같은 외부 ID는 별도 공고로 저장됐다.
- 실행: 격리된 PostgreSQL 17의 `devjob_s07_test` DB에서 `gradlew.bat build dbTest --offline --no-daemon`을 실행했다. 일반 테스트 36건과 DB 테스트 10건(기존 연결/HTTP 회귀 2건, S07 8건)이 통과했다. DB 테스트는 `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD` 환경 설정이 필요하며 S07 테스트는 테스트 DB 이름이 일치할 때만 실행한다. 실제 외부 연동·CRM API 경로 검증은 S07 범위 밖이다.
