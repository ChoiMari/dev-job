# DevJob User Flow

## 1. 문서 목적

본 문서는 **DevJob**에서 사용자가 수행하는 주요 업무 흐름(User Flow)을 정의한다.

`requirements.md`가 DevJob에서 **무엇을 제공해야 하는지**를 정의한다면, 본 문서는 사용자가 실제로 **어떤 목적을 가지고 어떤 순서로 기능을 사용하는지**를 정의한다.

### 관련 문서

* `requirements.md` — 제품 및 기능 요구사항
* `user-flow.md` — 사용자 행동 및 서비스 흐름
* `ui-spec.md` — 화면 및 UI 명세
* `architecture.md` — 시스템 구조
* `erd.md` — 데이터 모델
* `api-spec.md` — API 계약

---

# 2. 전체 서비스 흐름

DevJob의 핵심 흐름은 다음과 같다.

```text
회원가입 / 로그인
       ↓
프로필 및 역량 등록
       ↓
프로젝트 / 기술 스택 등록
       ↓
채용공고 탐색
       ↓
채용공고 상세 확인
       ↓
AI 채용공고 분석
       ↓
내 역량과 비교
       ↓
지원 여부 판단
       ↓
관심 / 지원 예정 / 지원 완료
       ↓
지원 상태 관리
       ↓
면접 / 최종 결과 기록
       ↓
채용시장 데이터 분석
       ↓
부족한 역량 확인
       ↓
학습 우선순위 설정
       ↓
다시 채용공고 탐색
```

DevJob은 단순한 채용공고 검색 서비스가 아니라,

> **채용공고 탐색 → 역량 비교 → 지원 → 결과 관리 → 역량 보완 → 다시 지원**

의 반복적인 취업 준비 사이클을 지원한다.

---

# 3. 사용자 유형

MVP에서는 하나의 핵심 사용자 유형을 대상으로 한다.

## 일반 사용자

개발자 취업을 준비하는 구직자.

주요 목적:

1. 원하는 개발자 채용공고 찾기
2. 내 역량과 채용공고 요구사항 비교
3. 지원할 공고 결정
4. 지원 현황 관리
5. 부족한 기술 확인
6. 취업 준비 우선순위 결정

# 4. 회원가입 / 로그인 Flow

## FLOW-001 회원가입

```text
회원가입
   ↓
이메일 / 비밀번호 입력
   ↓
중복 및 유효성 검증
   ↓
계정 생성
   ↓
로그인
   ↓
프로필 설정
```

회원가입 직후에는 기본 프로필을 설정할 수 있도록 한다.

S03 구현 범위에서는 계정 생성 후 로그인 화면으로 이동하며 자동 로그인하지 않는다. 프로필 설정은 S04에서 구현했다. 회원가입의 비밀번호 확인은 화면에서만 검증하고 API에는 이메일·비밀번호만 보낸다.

S04에서는 로그인 후 `#/profile`에서 첫 프로필을 저장할 수 있다. 기존 사용자는 같은 화면에서 수정한다. 기술 스택 추가는 S05에서 연결하며 S04 저장 뒤에는 프로필 화면에 머문다.

---

## FLOW-002 로그인

S03에서는 로그인 성공 후 기존 기본 화면으로 이동한다. Dashboard 기능은 S16에서 구현한다. 미인증 사용자의 기본 화면·공통 상태 화면 접근은 로그인 화면으로 이동하며, 새로고침 시 현재 사용자 API로 서버 인증 상태를 확인한다.

```text
로그인 화면
   ↓
이메일 / 비밀번호 입력
   ↓
인증
   ↓
성공
   ↓
Dashboard
```

로그인 실패:

```text
로그인
  ↓
인증 실패
  ↓
오류 메시지
  ↓
다시 입력
```

---

## FLOW-002A 로그아웃 (S03)

S03 로그아웃 Flow: 로그아웃 클릭 → CSRF 준비 → 서버 세션 무효화·쿠키 삭제 → 로그인 화면. 이후 보호 경로와 현재 사용자 API에 다시 접근하면 인증을 요구한다. 서버 오류·네트워크 오류로 로그아웃이 실패하면 성공으로 표시하지 않고 오류와 재시도를 제공한다. 만료된 세션의 `401`은 로그인 화면으로 이동한다.

# 5. 초기 프로필 설정 Flow

## FLOW-003 첫 프로필 설정

회원가입 이후 사용자는 자신의 취업 프로필을 설정한다.

```text
회원가입
   ↓
프로필 설정
   ↓
희망 직무
   ↓
희망 지역
   ↓
경력 정보
   ↓
기술 스택
   ↓
학력 / 자격증
   ↓
프로필 저장
   ↓
Dashboard
```

### 입력 정보

* 희망 직무
* 희망 지역
* 경력
* 기술 스택
* 학력
* 자격증
* 기타 취업 관련 정보

프로필 정보는 이후 채용공고와의 역량 비교에 사용한다.

# 6. 기술 역량 관리 Flow

## FLOW-004 기술 추가

```text
Profile
   ↓
기술 스택
   ↓
기술 추가
   ↓
Skill 검색
   ↓
Skill 선택
   ↓
숙련도 / 경험 정보 입력
   ↓
저장
```

사용자가 입력한 기술명은 가능한 경우 DevJob 내부의 표준 Skill과 연결한다.

예:

```text
사용자 입력
Postgres

        ↓

표준 Skill
PostgreSQL
```

# 7. 프로젝트 등록 Flow

## FLOW-005 프로젝트 등록

```text
Project Management
       ↓
프로젝트 추가
       ↓
프로젝트 정보 입력
       ↓
사용 기술 선택
       ↓
역할 / 경험 입력
       ↓
GitHub / 배포 URL 입력
       ↓
저장
```

프로젝트에 연결된 기술은 사용자 역량 분석에도 활용한다.

S06 구현: `#/projects` → 프로젝트 추가 → `#/projects/new`에서 정보와 표준 기술 선택 → 저장 → `#/projects/{projectId}` 상세로 이동한다. 상세에서 수정·저장 또는 취소, 삭제 확인·취소를 제공하며 삭제 성공 후 목록으로 돌아간다. 새로고침은 저장값을 재조회한다. 실패한 저장은 입력·기술 선택을 유지하고 조회·기술 검색 실패는 재시도한다. 프로젝트의 사용 기술은 보유 기술 목록을 자동 변경하지 않으며, 역량 비교 기능 연결은 S13에서 진행한다.

예:

```text
프로젝트
   │
   ├── Java
   ├── Spring Boot
   ├── PostgreSQL
   └── Docker
```

# 8. 채용공고 수집 Flow

## FLOW-006 외부 채용공고 수집

DevJob은 외부 채용 데이터 소스를 통해 채용공고를 수집한다.

```text
Job Source
    ↓
외부 API 요청
    ↓
원본 채용 데이터 수신
    ↓
데이터 변환
    ↓
표준 JobPosting 구조로 변환
    ↓
중복 확인
    ↓
저장
```

S09 확정 범위는 개인회원에게 허용된 공채속보 목록의 내부 명시적 수집이며 구현·검증 완료다. 한 번에 한 페이지만 요청하고 자동 호출·공개 수집 API는 없다. 본문·지역·경력·날짜는 이번 목록 매핑에서 null이다. 외부 실패는 저장된 공고 조회·기존 데이터 처리를 중단시키지 않는다. Work24 일반 채용정보 목록·상세와 공채속보 상세는 S09 수집 범위에서 제외한다. 사람인 보완 연동은 별도 승인 확인 후 추가하며 고용24 공고의 빈 필드와 임의 병합하지 않는다.

외부 데이터 소스가 여러 개일 경우 각각의 데이터 형식을 DevJob 내부의 공통 구조로 변환한다.

```text
Work24 API ──────┐
                 │
Saramin API ─────┼──→ Job Source Adapter
                 │             ↓
Future API ──────┘      Normalized JobPosting
```

# 9. 채용공고 탐색 Flow

## FLOW-007 채용공고 검색

S08에서는 로그인 후 메뉴의 `채용공고` → 저장 공고 검색·기본 필터 → 페이지 이동 → 공고 제목 선택 → 상세로 이동한다. 검색·필터 제출 시 첫 페이지로 돌아가며, 조건·정렬·페이지는 `#/jobs?...`에 저장한다. 상세의 목록 링크는 이전 조건·페이지를 복원한다. 빈 검색 결과는 조건 변경, 범위 밖 페이지는 첫 페이지 이동을 제공한다. 로딩·실패 재시도와 세션 만료 시 기존 S03 로그인 이동을 적용한다. S11에서 내 지원 상태 필터를 연결했고 기술·적합도 필터는 후속 S12~S13 범위다.

```text
채용공고
   ↓
검색어 입력
   ↓
검색
   ↓
검색 결과
   ↓
필터 / 정렬
   ↓
채용공고 선택
   ↓
상세 화면
```

### 검색 조건

사용자는 다음 조건으로 채용공고를 좁힐 수 있다.

* 검색어
* 기술
* 지역
* 경력
* 고용 형태
* 마감일
* 적합도
* 지원 상태

# 10. 채용공고 상세 확인 Flow

## FLOW-008 채용공고 상세

S08 상세 경로는 `#/jobs/{jobId}`다. 분석이 없어도 회사·채용 조건·게시/마감일·저장 원문과 외부 원문 링크(새 창)를 보여준다. 본문이 없으면 외부 원문 확인을 안내한다. 없는 공고는 별도 안내와 목록 복귀, 조회 실패는 재시도를 제공한다. 북마크와 지원 등록·내 지원 상태는 S10·S11에서 각각 연결했으며 AI 분석 요청은 S12에서 연결한다.

```text
Job List
   ↓
Job 선택
   ↓
Job Detail
   ├── 회사 정보
   ├── 채용 조건
   ├── 기술 요구사항
   ├── 채용공고 원문
   └── 지원 관련 정보
```

사용자는 상세 화면에서 다음 행동을 수행할 수 있다.

* 관심 공고 저장
* 지원 상태 등록
* AI 분석 요청
* 외부 채용 페이지 이동

# 11. AI 채용공고 분석 Flow

## FLOW-009 AI 분석 요청

AI 분석은 사용자가 필요할 때 실행하거나 아직 분석되지 않은 공고에 대해 실행할 수 있다.

```text
Job Detail
   ↓
AI 분석 요청
   ↓
분석 상태 확인
   ↓
채용공고 텍스트 전달
   ↓
LLM 분석
   ↓
구조화된 결과 생성
   ↓
결과 검증
   ↓
Skill 표준화
   ↓
DB 저장
   ↓
분석 결과 표시
```

---

## 11.1 AI 분석 결과

AI는 채용공고에서 기술 및 요구사항을 추출한다.

예:

```text
채용공고

Java / Spring Boot / PostgreSQL 필수
Docker / AWS 우대

        ↓

AI 분석

REQUIRED
- Java
- Spring Boot
- PostgreSQL

PREFERRED
- Docker
- AWS
```

---

# 12. AI 분석 상태 Flow

AI 분석은 다음 상태를 가질 수 있다.

```text
PENDING
   ↓
분석 실행
   ↓
COMPLETED
```

실패할 경우:

```text
PENDING
   ↓
분석 실행
   ↓
FAILED
   ↓
재시도 가능
```

---

## 12.1 AI 실패 시

AI 분석이 실패하더라도 기본 채용공고 기능은 사용할 수 있어야 한다.

```text
AI 분석 실패
    ↓
실패 상태 저장
    ↓
채용공고 기본 정보는 정상 제공
    ↓
사용자가 필요할 때 재분석
```

즉,

> AI 기능의 장애가 CRM 전체 장애로 이어지지 않는다.

# 13. AI 분석 결과 재사용 Flow

이미 분석된 채용공고를 다시 조회할 경우 LLM을 다시 호출하지 않는다.

```text
Job Detail
   ↓
AI 분석 결과 존재?
   ├── YES → 저장된 결과 사용
   │
   └── NO → AI 분석 실행
```

이를 통해 불필요한 LLM 호출과 비용을 줄인다.

# 14. 사용자 역량 비교 Flow

## FLOW-010 내 역량 vs 채용공고 비교

AI 분석 결과가 준비되면 사용자의 기술과 비교할 수 있다.

```text
사용자 Profile
       +
사용자 Skills
       +
Projects
       ↓
Job Required / Preferred Skills
       ↓
Skill Normalization
       ↓
Skill Matching
       ↓
결과 생성
```

예:

```text
채용공고 요구사항

필수
✓ Java
✓ Spring Boot
✓ PostgreSQL
✕ AWS

우대
✓ Docker
✕ Redis
```

# 15. Skill Gap Flow

## FLOW-011 부족 역량 확인

사용자는 자신에게 부족한 기술을 확인한다.

```text
채용공고 분석
      ↓
Required Skills
      ↓
내 Skills와 비교
      ↓
Missing Skills
      ↓
Skill Gap
```

예:

```text
내 역량
Java
Spring Boot
PostgreSQL
Docker

채용공고
Java
Spring Boot
PostgreSQL
Docker
AWS
Redis

        ↓

부족 역량

AWS
Redis
```

# 16. 관심 공고 Flow

## FLOW-012 공고 저장

S10 구현: 로그인 → 공고 목록/상세에서 `관심 공고 저장` → `#/bookmarks` 목록 확인 → 상세 재조회 또는 `저장 해제`. 새로고침 후에도 서버의 사용자별 상태를 조회한다. 관심 목록의 상세 복귀는 원래 페이지를 보존한다. 저장·해제 실패는 기존 상태와 재시도 가능한 안내를 유지하며 이미 저장/해제된 경우 실제 상태를 재조회한다. 빈 목록·페이지 범위 초과·조회 오류/재시도를 구분한다. 다른 사용자 북마크는 조회·삭제하지 않고 지원·AI 등록을 강제하지 않는다.

```text
Job Detail
   ↓
저장하기
   ↓
Bookmark 생성
   ↓
관심 공고에 표시
```

저장된 공고는 이후 다시 확인할 수 있다.

# 17. 지원 Flow

## FLOW-013 지원 예정 등록

S11 구현 흐름: 공고 상세 → 지원 등록하기 → 관심·지원 예정·지원 완료 중 초기 상태 선택 → 선택적 메모·일정 입력(지원 완료는 지원일 필수) → 저장 → 내 지원 현황 배지 → 지원 관리로 이동한다. 등록은 외부 사이트에 실제 지원을 제출하는 기능이 아니며, 공고 원문 링크에서 별도로 진행한다. 같은 사용자·공고 재등록은 충돌을 안내한다. 북마크를 자동 생성하지 않는다.

지원 관리 `#/applications`에서 상태 필터·페이지를 선택하고 카드 → 지원 상세에서 메모·일정 또는 허용된 다음 상태를 저장한다. 최초 등록과 모든 실제 상태 변경은 이력에 표시한다. 변경 성공은 재조회·새로고침 후 유지되고 실패 시 초안과 재시도 경로를 제공한다. 상세 → 목록 복귀는 선택한 상태·페이지를 복원한다. 종료 상태는 추가 전이를 제공하지 않는다. 상세·편집·이력은 소유자만 접근할 수 있다.

사용자가 공고에 지원하기로 결정한다.

```text
Job Detail
   ↓
지원하기
   ↓
지원 예정 등록
   ↓
Application 생성
   ↓
지원 관리에 표시
```

# 24. 학습 우선순위 Flow

# 26. 취업 준비 반복 Cycle

DevJob의 핵심 사용자 경험은 반복적인 취업 준비 Cycle이다.

```text
┌───────────────────────────────────────┐
│                                       │
│       채용공고 탐색                   │
│             ↓                         │
│       AI 요구사항 분석                │
│             ↓                         │
│       내 역량 비교                    │
│             ↓                         │
│       지원 여부 결정                  │
│             ↓                         │
│       지원 및 상태 관리               │
│             ↓                         │
│       결과 확인                       │
│             ↓                         │
│       부족 역량 확인                  │
│             ↓                         │
│       학습 / 프로젝트 보완            │
│             ↓                         │
│       다시 채용공고 탐색              │
│             │                         │
│             └─────────────────────────┘
│                                       │
└───────────────────────────────────────┘
```

이 반복 Cycle이 DevJob의 핵심 서비스 흐름이다.

# 30. 사용자 행동의 핵심 원칙

DevJob의 주요 사용자 행동은 다음 네 가지 질문으로 설명할 수 있어야 한다.

### 1. 어디에 지원할까?

→ 채용공고 탐색 / 검색 / 필터

### 2. 내가 지원해도 될까?

→ AI 분석 / 역량 비교 / 적합도

### 3. 지금 어디까지 진행됐지?

→ 지원 관리 / 상태 이력 / 일정

### 4. 뭘 더 공부해야 하지?

→ Skill Gap / 채용시장 분석 / 학습 우선순위

이 네 가지 질문을 중심으로 서비스의 주요 화면과 기능을 연결한다.

# 32. Flow와 UI의 관계

User Flow와 UI는 다음과 같이 연결된다.

```text
User Flow                  UI

회원가입             →     UI-001 Login
                              ↓
Dashboard            →     UI-002 Dashboard
                              ↓
채용공고 탐색        →     UI-003 Job List
                              ↓
채용공고 확인        →     UI-004 Job Detail
                              ↓
지원 관리            →     UI-005 Application Management
                              ↓
역량 분석            →     UI-006 Skill Analysis
                              ↓
프로필 관리          →     UI-007 Profile
                              ↓
시장 분석            →     UI-008 Market Analytics
                              ↓
프로젝트 관리        →     UI-009 Project Management
                              ↓
캐릭터                →     UI-010 Character
```

하나의 User Flow가 반드시 하나의 화면에 대응할 필요는 없다.

예를 들어 AI 분석은 Job Detail 내부에서 실행되고 결과 역시 Job Detail 또는 Skill Analysis에서 활용할 수 있다.

# 33. Agent 작업 시 User Flow 준수

Coding Agent는 기능을 구현할 때 해당 기능이 어떤 User Flow에 속하는지 확인한다.

예:

```text
"채용공고 저장 기능 구현"
        ↓
FLOW-012 관심 공고 Flow 확인
        ↓
UI-003 / UI-004 확인
        ↓
Application / Bookmark 데이터 확인
        ↓
API Specification 확인
        ↓
구현
```

문서에 정의되지 않은 사용자 흐름을 임의로 추가하지 않는다.

기능 구현 과정에서 기존 Flow와 충돌하는 요구사항이 발견되면 구현 전에 확인한다.
