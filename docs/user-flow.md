# DevJob User Flow

## 1. 문서 목적

본 문서는 **DevJob**에서 사용자가 수행하는 주요 업무 흐름(User Flow)을 정의한다.

`requirements.md`가 DevJob에서 **무엇을 제공해야 하는지**를 정의한다면, 본 문서는 사용자가 실제로 **어떤 목적을 가지고 어떤 순서로 기능을 사용하는지**를 정의한다.

### 관련 문서

* `requirements.md` — 제품 및 기능 요구사항
* `user-flow.md` — 사용자 행동 및 서비스 흐름
* `ui-spec.md` — 화면 및 UI 명세
* `architecture.md` — 시스템 구조
* `erd.md` — 데이터 모델
* `api-spec.md` — API 계약

---

# 2. 전체 서비스 흐름

DevJob의 핵심 흐름은 다음과 같다.

```text
회원가입 / 로그인
       ↓
프로필 및 역량 등록
       ↓
프로젝트 / 기술 스택 등록
       ↓
채용공고 탐색
       ↓
채용공고 상세 확인
       ↓
AI 채용공고 분석
       ↓
내 역량과 비교
       ↓
지원 여부 판단
       ↓
관심 / 지원 예정 / 지원 완료
       ↓
지원 상태 관리
       ↓
면접 / 최종 결과 기록
       ↓
채용시장 데이터 분석
       ↓
부족한 역량 확인
       ↓
학습 우선순위 설정
       ↓
다시 채용공고 탐색
```

DevJob은 단순한 채용공고 검색 서비스가 아니라,

> **채용공고 탐색 → 역량 비교 → 지원 → 결과 관리 → 역량 보완 → 다시 지원**

의 반복적인 취업 준비 사이클을 지원한다.

# 4. 회원가입 / 로그인 Flow

프론트 전면 개편의 로그인 전 첫 접속 흐름은 [공개 홈 요구사항 FR-P00](frontend-redesign-requirements.md#3-페이지별-요구사항)을 따른다. `#/`에서 현재 사용자 조회가 `401`이면 공개 홈에서 로그인·회원가입으로 이동하고, 인증된 사용자이면 같은 경로에 대시보드를 표시한다. 인증 확인 중에는 화면을 먼저 노출하지 않으며 조회 실패에는 재시도를 제공한다. 다른 보호 경로에 미인증으로 직접 진입하면 기존처럼 로그인 화면으로 이동한다. 아래 S03 흐름은 기존 구현 기록이며 로그인 성공 후 대시보드 이동, 가입 후 로그인 안내, 로그아웃 후 로그인 이동은 유지한다.

로그인 화면의 `비밀번호를 잊으셨나요?`는 `#/forgot-password`로 이동한다. 이 화면은 이메일 입력과 재설정 기능 준비 중 안내만 제공한다. 전송 버튼은 비활성화되어 있으며 Backend 요청, 메일 전송, 비밀번호 변경은 수행하지 않는다. 로그인 화면으로 돌아갈 수 있다.

## FLOW-001 회원가입

```text
회원가입
   ↓
이메일 / 비밀번호 입력
   ↓
중복 및 유효성 검증
   ↓
계정 생성
   ↓
로그인
   ↓
프로필 설정
```

회원가입 직후에는 기본 프로필을 설정할 수 있도록 한다.

S03 구현 범위에서는 계정 생성 후 로그인 화면으로 이동하며 자동 로그인하지 않는다. 프로필 설정은 S04에서 구현했다. 회원가입의 비밀번호 확인은 화면에서만 검증하고 API에는 이메일·비밀번호만 보낸다.

S04에서는 로그인 후 `#/profile`에서 닉네임을 포함한 첫 프로필을 저장할 수 있다. 저장 뒤 헤더에는 이메일 대신 닉네임이 표시된다. 기존 사용자는 같은 화면에서 수정하되 로그인 ID인 이메일은 읽기 전용이다. 기술 스택 추가는 S05에서 연결하며 S04 저장 뒤에는 프로필 화면에 머문다.

---

## FLOW-002 로그인

로그인 성공 후 대시보드로 이동한다. 미인증 사용자의 대시보드·공통 상태 화면 접근은 로그인 화면으로 이동하며, 새로고침 시 현재 사용자 API로 서버 인증 상태를 확인한다.

```text
로그인 화면
   ↓
이메일 / 비밀번호 입력
   ↓
인증
   ↓
성공
   ↓
Dashboard
```

로그인 실패:

```text
로그인
  ↓
인증 실패
  ↓
오류 메시지
  ↓
다시 입력
```

---

## FLOW-002A 로그아웃 (S03)

S03 로그아웃 Flow: 로그아웃 클릭 → CSRF 준비 → 서버 세션 무효화·쿠키 삭제 → 로그인 화면. 이후 보호 경로와 현재 사용자 API에 다시 접근하면 인증을 요구한다. 서버 오류·네트워크 오류로 로그아웃이 실패하면 성공으로 표시하지 않고 오류와 재시도를 제공한다. 만료된 세션의 `401`은 로그인 화면으로 이동한다.

# 6. 기술 역량 관리 Flow

## FLOW-004 기술 추가

현재 프로필 화면은 표준 기술을 검색해 추가·삭제하고, 추가 모달에서 숙련도를 선택하거나 등록 후 수정한다. 경험 개월 수는 API에 저장할 수 있지만 이 화면에서는 입력·표시하지 않는다.

```text
Profile
   ↓
기술 스택
   ↓
Skill 검색
   ↓
Skill 선택
   ↓
기술 추가
   ↓
필요하면 보유 기술 메뉴에서 숙련도 수정
```

사용자가 입력한 기술명은 가능한 경우 DevJob 내부의 표준 Skill과 연결한다.

예:

```text
사용자 입력
Postgres

        ↓

표준 Skill
PostgreSQL
```

# 7. 프로젝트 등록 Flow

## FLOW-005 프로젝트 등록

```text
Project Management
       ↓
프로젝트 추가
       ↓
프로젝트 정보 입력
       ↓
사용 기술 선택
       ↓
역할 / 경험 입력
       ↓
GitHub / 배포 URL 입력
       ↓
저장
```

프로젝트에 연결된 기술은 사용자 역량 분석에도 활용한다.

S06 구현: `#/projects` → 프로젝트 추가 → `#/projects/new`에서 정보와 표준 기술 선택 → 저장 → `#/projects/{projectId}` 상세로 이동한다. 상세에서 수정·저장 또는 취소, 삭제 확인·취소를 제공하며 삭제 성공 후 목록으로 돌아간다. 새로고침은 저장값을 재조회한다. 실패한 저장은 입력·기술 선택을 유지하고 조회·기술 검색 실패는 재시도한다. 프로젝트의 사용 기술은 보유 기술 목록을 자동 변경하지 않으며, 역량 비교 기능은 S13에서 연결했다.

예:

```text
프로젝트
   │
   ├── Java
   ├── Spring Boot
   ├── PostgreSQL
   └── Docker
```

# 8. 채용공고 수집 Flow

## FLOW-006 외부 채용공고 수집

DevJob은 외부 채용 데이터 소스를 통해 채용공고를 수집한다.

```text
Job Source
    ↓
외부 API 요청
    ↓
원본 채용 데이터 수신
    ↓
데이터 변환
    ↓
표준 JobPosting 구조로 변환
    ↓
중복 확인
    ↓
저장
```

S09 확정 범위는 개인회원에게 허용된 공채속보 목록의 내부 명시적 수집이며 구현·검증 완료다. 한 번에 한 페이지만 요청하고 자동 호출·공개 수집 API는 없다. 본문·지역·경력·날짜는 이번 목록 매핑에서 null이다. 외부 실패는 저장된 공고 조회·기존 데이터 처리를 중단시키지 않는다. Work24 일반 채용정보 목록·상세와 공채속보 상세는 S09 수집 범위에서 제외한다. 청년일자리 공공기관 채용정보는 사용자 목록과 분리된 인증·CSRF 보호 수동 POST로 지정한 시작 page부터 최대 3페이지와 선택 공고의 상세를 수집한다. 사용자는 저장된 공고 목록에서 출처를 선택해 탐색한다. 고용24 공고의 빈 필드와 임의 병합하지 않는다. 상세 실패 시 해당 공고의 기존 상세는 보존하고 부분 실패를 표시하며 저장된 목록 조회는 계속 가능하다.

외부 데이터 소스가 여러 개일 경우 각각의 데이터 형식을 DevJob 내부의 공통 구조로 변환한다.

```text
Work24 API ──────┐
                 │
청년일자리 API ────┼──→ Job Source Adapter
                 │             ↓
Future API ──────┘      Normalized JobPosting
```

# 9. 채용공고 탐색 Flow

## FLOW-007 채용공고 검색

S08에서는 로그인 후 메뉴의 `채용공고` → 저장 공고 검색·기본 필터 → 페이지 이동 → 공고 제목 선택 → 상세로 이동한다. 검색·필터 제출 시 첫 페이지로 돌아가며, 조건·정렬·페이지는 `#/jobs?...`에 저장한다. 상세의 목록 링크는 이전 조건·페이지를 복원한다. 빈 검색 결과는 조건 변경, 범위 밖 페이지는 첫 페이지 이동을 제공한다. 로딩·실패 재시도와 세션 만료 시 기존 S03 로그인 이동을 적용한다. S11에서 내 지원 상태 필터, S13에서 기술·최소 일치도 필터와 일치도 정렬을 연결했다. 공공기관·고용24 출처 필터도 같은 저장 공고 GET과 URL 조건을 사용한다.

2026-10-07 ALIO 내부 수집 흐름: 인증된 클라이언트의 별도 POST에서 시작 page·최대 3페이지를 지정 → 진행 중인 정보통신 NCS 목록에서 개발·데이터·보안·인프라 중심 제목의 공고를 선별해 저장 → 사용자는 DB에 저장된 공고를 검색. 사용자 채용공고 화면은 수집 요청을 표시하거나 호출하지 않는다. 전체 저장 공고 선택 시 이전 공고와 북마크도 계속 탐색할 수 있다.

후속 검색 UI에서는 상세 필터가 결과 위에 오고 전체 저장 공고가 기본 검색 범위다. 경력 체크박스는 여러 구간을 선택해 `careerBands`의 OR 검색으로 보내며, 고용 형태는 클릭해서 한 값을 선택하고 지역은 전국 시도 중 하나를 선택한다. 마감일 빠른 선택은 하나의 `deadlineBefore` 날짜로 보낸다. 최소 기술 일치도는 사용자 기술과 완료된 공고 분석이 있어 계산된 공고만 대상으로 한다. 이전 검색 주소의 추가 조건은 안내 후 초기화하거나 새 검색으로 해제한다.

```text
채용공고
   ↓
검색어 입력
   ↓
검색
   ↓
검색 결과
   ↓
필터 / 정렬
   ↓
채용공고 선택
   ↓
상세 화면
```

### 검색 조건

사용자는 다음 조건으로 채용공고를 좁힐 수 있다.

* 검색어
* 기술
* 지역
* 경력
* 고용 형태
* 마감일
* 적합도
* 지원 상태

# 10. 채용공고 상세 확인 Flow

## FLOW-008 채용공고 상세

S08 상세 경로는 `#/jobs/{jobId}`다. 분석이 없어도 회사·채용 조건·게시/마감일·저장 원문과 외부 원문 링크(새 창)를 보여준다. 본문이 없으면 외부 원문 확인을 안내한다. 없는 공고는 별도 안내와 목록 복귀, 조회 실패는 재시도를 제공한다. 북마크와 지원 등록·내 지원 상태는 S10·S11에서 각각 연결했고 S12는 분석 요청·상태 확인·결과·실패 재시도를 연결했다.

```text
Job List
   ↓
Job 선택
   ↓
Job Detail
   ├── 회사 정보
   ├── 채용 조건
   ├── 기술 요구사항
   ├── 채용공고 원문
   └── 지원 관련 정보
```

사용자는 상세 화면에서 다음 행동을 수행할 수 있다.

* 관심 공고 저장
* 지원 상태 등록
* AI 분석 요청
* 외부 채용 페이지 이동

# 11. AI 채용공고 분석 Flow

## FLOW-009 AI 분석 요청

AI 분석은 사용자가 필요할 때 실행하거나 아직 분석되지 않은 공고에 대해 실행할 수 있다.

S12 구현은 상세에서 사용자가 요청할 때만 비동기 작업을 접수한다. `POST`는 새 요청·진행 중이면 `202 PENDING`, 완료된 결과가 있으면 외부 AI 재호출 없이 `200 COMPLETED`를 반환한다. 화면은 `GET`으로 현재 계정의 요청 상태를 확인하고 실패 상태에서는 재시도, 완료 상태에서는 같은 `AI 분석하기` 버튼으로 계정별 후보 반영을 다시 요청할 수 있다. 키 미설정 시 새 요청은 `503`이며 분석 행을 만들지 않는다. 분석 실패·미설정 키는 저장된 공고, 북마크, 지원 조회에 영향을 주지 않는다.

```text
Job Detail
   ↓
AI 분석 요청
   ↓
분석 상태 확인
   ↓
채용공고 텍스트 전달
   ↓
LLM 분석
   ↓
구조화된 결과 생성
   ↓
결과 검증
   ↓
Skill 표준화
   ↓
DB 저장
   ↓
분석 결과 표시
```

# 16. 관심 공고 Flow

## FLOW-012 공고 저장

S10 구현: 로그인 → 공고 목록/상세에서 `관심 공고 저장` → `#/bookmarks` 목록 확인 → 상세 재조회 또는 `저장 해제`. 새로고침 후에도 서버의 사용자별 상태를 조회한다. 관심 목록의 상세 복귀는 원래 페이지를 보존한다. 관심 해제는 목록 카드에서 먼저 해제 예정 안내를 표시하고 취소하거나 확정할 수 있다. 확정 후에는 해당 카드의 빈 북마크를 다시 눌러 재등록할 수 있으며, 재등록 전 새로고침하면 목록에서 사라진다. 저장·해제 실패는 기존 상태와 재시도 가능한 안내를 유지하며 이미 저장/해제된 경우 실제 상태를 재조회한다. 빈 목록·페이지 범위 초과·조회 오류/재시도를 구분한다. 다른 사용자 북마크는 조회·삭제하지 않고 지원 등록은 북마크와 독립적이다. 새 AI 분석 요청에는 본인 북마크가 필요하다.

직접 등록 흐름: `#/bookmarks`에서 `+ 공고 직접 등록` → `#/bookmarks/new`의 별도 입력 페이지에서 URL·기업명·제목과 선택 정보 및 분석에 사용할 공고 본문을 입력 → 개인 관심공고 저장 → 수집 공고 북마크와 통합 목록에서 원문·수정·삭제·지원 등록을 관리한다. 지원 등록 후에는 목록의 중복된 지원 현황 박스를 숨기고 상태 배지와 지원 관리에서 확인한다. 본문이 있는 개인 공고는 관심 목록에서 명시적으로 AI 분석을 요청하고 완료된 필수·우대 기술을 다시 확인할 수 있다. 본문·제목이 바뀌면 이전 개인 분석은 무효화된다. 삭제는 목록 카드에서 먼저 삭제 예정으로 표시하고 다시 눌러 취소할 수 있다. 별도 삭제 확정 버튼을 누르면 목록에서 숨기되 기존 지원 상태·이력은 유지한다. 채용공고 목록/상세에는 직접 등록 진입점이 없다. 수집 공고 상세의 AI 분석 버튼은 표시하며 관심 저장 후 활성화되고, 결과는 관심 목록에도 표시된다.

```text
Job Detail
   ↓
저장하기
   ↓
Bookmark 생성
   ↓
관심 공고에 표시
```

저장된 공고는 이후 다시 확인할 수 있다.

# 17. 지원 Flow

## FLOW-013 지원 예정 등록

지원 등록 흐름: 공고 상세와 지원 관리의 `지원 내역 추가` 모달에서 지원 예정·서류 접수·서류 합격·면접·최종 합격·불합격·철회 중 현재 상태를 선택한다 → 선택적 메모·일정과 실제 지원일을 입력한다(서류 접수 이후 진행 상태는 지원일 필수, 철회는 선택) → 저장 → 지원 관리에서 확인한다. 모달에서는 관심 공고·전체 공고를 검색해 선택하고, 목록에 없는 공고는 직접 등록 페이지로 이동한다. 등록은 외부 사이트에 실제 지원을 제출하는 기능이 아니며, 공고 원문 링크에서 별도로 진행한다. 같은 사용자·공고 재등록은 충돌을 안내한다. 북마크를 자동 생성하지 않는다.

관심 공고 목록에서는 지원 기록이 없는 수집 공고와 직접 등록 공고에 `지원 등록하기` 버튼을 표시한다. 버튼을 누르면 해당 공고의 입력 폼을 펼치고, 등록 후 상태 배지와 지원 관리 링크로 확인한다.

지원 관리 `#/applications`에서는 서류 접수·서류 합격·면접·최종 합격·불합격·기타 6열에서 상태별 기록을 확인한다. 지원 예정·철회는 기타에서 구분하고 과거 관심 기록은 보드에서 제외한다. 각 상태의 초기 100건을 보고 더 보기로 나머지를 조회한다. 카드를 모든 열 사이에 드래그해 이동하며, 기타에서는 지원 예정 또는 철회를 선택한다. 지원 예정으로 옮기면 기존 지원일을 지우고, 지원일이 없는 기록을 서류 접수 이후 단계로 옮길 때 날짜를 받는다. 카드 제목이나 메뉴의 수정을 누르면 보드 위 지원 상세 모달에서 저장된 상태·지원일과 값이 있는 지역·일정·메모, 공고 링크를 확인한다. 모달 머리말에서 수정하거나 삭제 확인창을 열 수 있다. 상태 변경 이력은 모달에 표시하지 않으며 서버의 이력 기록은 유지한다. 삭제는 확인 후 목록에서 숨긴다. 최초 등록과 모든 실제 상태 변경은 서버 이력에 남는다. 변경 성공은 재조회·새로고침 후 유지되고 실패 시 재시도 경로를 제공한다. 상세·편집·이력 API는 소유자만 접근할 수 있다.

사용자가 공고에 지원하기로 결정한다.

```text
Job Detail
   ↓
지원하기
   ↓
지원 예정 등록
   ↓
Application 생성
   ↓
지원 관리에 표시
```

# 29. 상태 전이 원칙

Application 상태는 사용자가 기록한 실제 지원 진행 상황을 반영한다. 보드에서는 `APPLIED`, `DOCUMENT_PASSED`, `INTERVIEW`, `FINAL_PASSED`, `REJECTED`, 기타(`PLANNED`·`WITHDRAWN`)를 보여준다. 사용자는 같은 상태와 `INTERESTED`를 제외한 모든 상태로 이동할 수 있다. 기존 `INTERESTED` 기록은 호환용으로 조회할 수 있지만 보드에는 표시하지 않는다. `PLANNED`로 이동하면 지원일을 비운다. 지원일이 없고 실제 지원 단계를 선택하면 날짜가 필요하며, `WITHDRAWN`에서는 선택이다. 최초 등록과 모든 실제 상태 변경은 이력에 남긴다.

## B03 개인 할 일 달력 흐름 (EXT-03)

1. 사용자는 `내 할 일`에서 월·주·일 달력을 이동하고 날짜의 점을 눌러 해당 날짜의 할 일을 본다. 오른쪽에는 전체 할 일 목록을 항상 표시한다.
2. 목록은 전체·진행 중·완료, 카테고리 태그, 제목·내용 검색, 최신순·기한순으로 좁힌다. 달력과 목록은 같은 실제 조회 결과를 사용한다. 넓은 화면에서는 달력을 한 줄 전체에 표시하고, 그 아래 선택 날짜 할 일과 전체 할 일을 같은 줄에 둔다. 두 할 일 카드 상단의 `＋` 버튼에서 할 일을 추가할 수 있다.
3. `할 일 추가`를 누르면 현재 화면 위에 등록 모달이 열린다. 제목을 누르면 상세 모달이 열리고 그 안에서 수정·완료·삭제한다. 날짜는 오늘로 시작하고 알림은 `알림 없음`이 기본이다. `기한 없음`을 체크하면 기한 없이 저장한다. 시간을 선택하지 않으면 23:59·Asia/Seoul 안내를 표시한다. 카테고리는 등록 모달에 펼쳐진 목록에서 고르며, `전체 보기` 버튼 없이 관리 버튼과 추가 `＋`를 제공한다. 등록 모달의 `＋`를 누르면 바로 카테고리 추가 모달이 열린다. 추가창 왼쪽 아래의 관리 버튼은 카테고리 관리창을 연다. 여기서 이름·7열 4행으로 표시한 28개 개별 픽셀 아이콘·색상 중 하나를 선택한다. 최대 20개 카테고리를 등록할 수 있고 이미지는 재사용한다. 관리 모달에서 드래그 정렬·수정·삭제할 수 있으며 사용 중인 카테고리 삭제는 오류를 표시한다. 대시보드 필터에는 `All`과 실제 할 일에 사용된 카테고리만 우선 표시하고, 많으면 더보기로 펼친다. 할 일 행의 알림을 메뉴 앞에 한 줄로 놓고, 메뉴는 카드 안에서 행을 늘려 표시하며 완료 시 제목과 기한에 취소선을 표시한다.
4. 상세에서 수정·삭제하거나 날짜·전체 목록의 체크박스로 완료 상태를 바꾼다. 변경 성공 시 서버 응답 상태를 반영하고 실패 시 오류를 표시한다.

## B04 관심 기업 관리 흐름 (EXT-05-01)

개편 목록에서 사용자는 기업명·메모·태그를 검색하고 산업·규모·지역·관심도·태그로 본인 기록을 필터링·정렬한다. 카드에서 웹사이트를 열고 즐겨찾기를 바꾸거나 수정·삭제 메뉴를 사용한다. 등록은 목록 위 모달의 기본/추가 정보 탭에서 진행하고, 산업·규모·지역·관심도·즐겨찾기·최대 5개 태그는 기존 기업 기록에 선택적으로 저장된다. 태그 관리 모달에서는 전체 30개 상한 안에서 이름·색상을 변경하고 드래그로 순서를 바꾼다. 이름 변경·삭제는 그 태그를 사용하던 본인 기록에도 반영된다.

1. 로그인 사용자는 기업 관리 목록에서 본인 기록을 페이지별로 조회한다. 빈 목록이면 등록으로 이동할 수 있다.
2. 기업명·웹사이트·메모·관리 상태를 저장하고 상세를 재조회한다. 같은 이름만으로 기업을 합치지 않으며 공고의 공용 Company와 자동 연결하지 않는다.
3. 상세에서 메모·상태 등을 수정한 뒤 저장 결과를 확인한다. 같은 사용자에게 같은 웹사이트 URL이 이미 있으면 중복 오류를 안내하고 입력을 유지한다.
4. 삭제는 대상 이름을 보여주고 다시 확인한다. 취소하면 기록을 유지하고, 삭제 뒤 상세 재접근은 없는 기록으로 안내한다. 기존 공고·지원 조회는 그대로 유지한다.

## F09 개편 화면 간 이동 (2026-10-11)

- 미인증 첫 `#/`은 공개 홈이고 로그인·회원가입으로 이동한다. 보호 경로를 직접 열면 로그인으로 이동하며, 인증된 `#/`은 대시보드다. 보호 API의 401은 세션 만료 안내가 있는 로그인 경로로 보낸다.
- 지원 상세 `#/applications/{id}`에서 `#/interviews/new?applicationId={id}`로 이동하면 지원 ID가 미리 입력된다. 면접 저장·상태는 지원의 `nextScheduleAt`이나 상태를 자동 변경하지 않는다.
- 면접 일정 등록·수정에서는 지원 ID 직접 입력 대신 본인 지원 목록에서 회사를 검색해 선택한다. 면접 단계·방식·메모는 면접 일정 자체에 저장되며 지원 기록으로 복사하지 않는다.
- 면접 일정 목록은 달력형·목록형을 전환하고 월·날짜·상태·검색 조건으로 기존 저장 일정을 찾는다. 연결된 지원 이력이 있을 때만 회사와 직무를 해당 지원에서 표시한다. 예정 일정은 사용자가 완료 또는 취소로 바꾸며, 완료와 취소 사이에는 먼저 예정 상태로 되돌린다. 면접 상태 변경은 지원 상태와 다음 일정을 바꾸지 않는다.
- 설정의 수신 설정에서 `#/notifications` 목록으로 이동한다. 목록의 면접/할 일 출처 링크는 각각 해당 상세 화면으로 이동한다.
- 공고·관심 공고와 이력서·자기소개서 화면에서 `#/recommendations`로 이동해 사용자가 문서 버전과 공고 후보를 다시 선택한다. 추천 결과의 직접 주소 `#/recommendations/{id}`는 저장 결과를 재조회한다.
- 직접 등록 공고는 `#/bookmarks/{id}`로 열려 직접 진입·새로고침·뒤로 가기가 가능하다. 관리자 배치 `#/admin/alio`는 일반 메뉴에 없으며 API의 권한 검사 결과를 따른다.


## 프로필 기술 관리 (V37)

사용자는 고정 기술을 검색해 보유 기술로 추가하거나 목록 밖 이름을 자기 계정의 직접 등록 기술로 추가한다. 직접 등록 기술은 그 계정 안에서만 수정·삭제한다. 숙련도는 고정·직접 등록 기술 모두 선택할 수 있으며 경험 개월 입력은 화면에서 받지 않는다. AI 공고 분석을 명시적으로 실행한 사용자는 완료된 결과의 기술을 별도 AI 후보로 본다. 다른 계정이 이미 분석한 관심 공고에도 `AI 분석하기` 버튼이 보이며, 내가 누르면 기존 완료 결과를 재사용해 내 후보에 반영하고 AI를 다시 호출하지 않는다. 공고나 결과를 조회하는 것만으로는 후보가 바뀌지 않는다. 후보에서 명시적으로 보유 기술에 추가하거나 삭제할 수 있으며, 다른 계정의 후보·직접 등록 기술은 보이지 않는다.
