# DevJob Exec Plan 작성 규칙

이 문서는 Codex가 **복잡한 작업을 시작하기 전** 작성하는 실행계획의 기준이다. `AGENTS.md`의 공통 작업 규칙을 보완하며, 기능 요구사항·DB 구조·API 계약 자체를 이 문서에 복제하지 않는다.

## 계획이 필요한 때

- 여러 파일, Backend의 여러 계층, Backend와 Frontend, 또는 여러 기능에 걸쳐 변경할 때 작성한다.
- DB·API·UI·사용자 흐름·아키텍처의 계약을 함께 바꿔야 하거나, 작업 단계를 나누어 검증해야 할 때 작성한다.
- 한 파일의 명확한 문구 수정이나 범위가 작은 단순 변경에는 별도 계획 문서를 만들지 않는다.
- 계획은 해당 작업의 실행 도구다. 계획을 위한 불필요한 파일을 저장소에 추가하지 않는다. 사용자가 계획 파일을 요청한 경우에만 지정된 위치에 저장한다.

## 작성 전 확인

1. 사용자 요청의 목표, 범위, 금지 사항, 완료 조건을 확인한다.
2. 관련 문서 **만** 읽는다. DB는 `docs/erd.md`, API는 `docs/api-spec.md`, 구조는 `docs/architecture.md`, UI는 `docs/ui-spec.md`, 사용자 흐름은 `docs/user-flow.md`, 요구사항은 `docs/requirements.md`, 개발 순서는 `docs/development-plan.md`를 기준으로 한다.
3. 기존 코드와 테스트, 현재 변경사항을 확인해 이미 구현된 부분과 사용자의 미완료 변경을 구분한다.
4. 문서 간 또는 문서와 코드 간 차이를 기록한다. 근거로 해결되지 않는 요구사항·설계 판단은 추측하지 않고 사용자에게 확인한다. 이미 받은 승인과 이번 요청의 범위는 다시 묻지 않는다.
5. 명확한 구현 세부사항은 기존 문서와 프로젝트의 일관성을 기준으로 합리적으로 결정하고, 사용자 결정이 필요한 사항만 질문한다.

## 계획에 포함할 내용

| 항목 | 적을 내용 |
| --- | --- |
| 목표·범위 | 사용자가 얻을 결과, 이번 작업에서 다루지 않을 범위 |
| 현재 상태 | 관련 구현·문서·테스트·작업 중 변경사항의 확인 결과 |
| 관련 문서 | 실제로 읽고 적용할 문서와 그 문서의 역할 |
| 변경 대상 | 예상 파일·모듈·계층, 외부 계약 및 데이터 영향 |
| 구현 단계 | 선행 관계에 따라 나눈 작고 검증 가능한 작업과 각 단계의 산출물 |
| 검증 방법 | 가능한 Build/Compile, 관련 테스트, 회귀 확인, 변경 파일·문서 정합성 확인 |
| 완료 조건 | 기능과 계약이 일치하는지 판단할 구체적 기준, 사용자에게 보고할 결과 |

## 실행과 갱신

- 각 단계를 마칠 때 산출물과 검증 결과를 확인한 뒤 다음 단계로 진행한다. 테스트는 마지막에 몰지 않고 관련 구현과 함께 수행한다.
- 구현 중 문서와 실제 동작이 달라지면 해당 문서를 함께 갱신한다. API 변경은 `docs/api-spec.md`, DB 변경은 `docs/erd.md`를 확인한다.
- 새 사실로 계획이 달라지면 변경 이유와 영향 범위를 계획에 반영한다. 요청하지 않은 기능·기술·리팩토링으로 범위를 넓히지 않는다.
- 완료 시 실제 변경 파일, 실행한 검증, 통과·미실행 항목, 남은 판단 사항을 보고한다. 문서만 바꾼 작업에서는 코드 빌드·테스트를 무리하게 실행하지 않고 문서 링크·내용·diff를 검토한다.
